    Firmware Unit Tests

    A unit test runs one small part of the code with chosen inputs and checks the result. The unit tests of the Teensy firmware run on your PC, without a Teensy. The tested code talks to stand-ins for the hardware and for the ROS connection, which the tests call fakes. PlatformIO, the tool that builds the firmware, also builds the tests into programs for the PC and runs them (PlatformIO's unit testing).

    This page runs one test first. Then it explains which of the two test frameworks a new test uses, and how to write a test suite. CI runs every suite on every pull request (Firmware unit tests on the Testing and CI page).

    Run the tests

    One test

    The goal of this first run is to check that a register write sends the register byte followed by the value byte. The test WireBusTest.WriteRegisterSendsRegisterAndValue checks exactly that, for the firmware's I2C bus code. Run it in the firmware container, which needs only Docker, from the root folder of your diffbot clone:

    The first run of an environment downloads what it needs from PlatformIO's registry, so it needs the internet. For native_googletest that is GoogleTest, for native Unity and rosserial. The libraries land in diffbot_firmware/.pio/libdeps/<environment>. Later runs of the same environment work without the internet. To be able to run every suite offline, run the command for every suite below once while you are online.

    The command has four parts:

    • .docker/firmware/run.sh: our script that runs a command in the firmware container, in the folder diffbot_firmware.
    • pio test -e native_googletest: PlatformIO's test command, with the environment that builds the GoogleTest suites. An environment is a section of platformio.ini that says what to build and how.
    • --filter googletest/test_wire_bus: the PlatformIO test suite, a folder below diffbot_firmware/test whose name starts with test_. PlatformIO builds each of these folders into one test program. --filter selects folders, not single tests.
    • --program-arg=--gtest_filter=…: an option that PlatformIO passes on to the test program (pio test's options). GoogleTest's option --gtest_filter runs only the tests whose full name matches (Running a Subset of the Tests).

    A test's full name has two parts. GoogleTest groups the tests of a program into GoogleTest test suites, and the name before the dot is that group, here WireBusTest. The name after the dot is the test. The program of googletest/test_wire_bus has twelve tests in two GoogleTest test suites, WireBusTest and ShortReads/WireBusShortReadTest. PlatformIO counts each test as a test case.

    After the tests of a suite with a failure, PlatformIO 6.2.0 prints Program received signal SIGHUP (Hangup) and gives the suite the status ERRORED. In this run, no signal was sent. The test program ends with the exit status 1 when a test fails, and PlatformIO reads a nonzero status as a signal's number. Signal 1 is SIGHUP. A program that really received the signal SIGHUP gets the same message. So the message doesn't tell you what went wrong: look for a failed check above it. A Unity suite with one failed test shows the same line.

    Why exit status 1 reads as SIGHUP: raise_for_status() in PlatformIO 6.2.0

    try:
        sig = signal.Signals(abs(return_code))

    Which framework for a new test

    The firmware's suites are written with two test frameworks, Unity and GoogleTest. A test framework is the library that provides the checks and reports which tests passed. Which framework a test uses depends on the code that it tests:

    • A new test of portable code: GoogleTest. The suite's folder is test/googletest/test_<name>/, and the environment native_googletest runs it. Portable code is code that builds on the PC. That is the firmware's core, the logic that includes no Arduino, rosserial or other vendor library header (Ports and adapters in the firmware's README). An adapter connects the core to a library or to the hardware, and most adapters need the Arduino core. An adapter that takes its library as a template argument, as WireBusT does below, is portable code too.
    • A test of the rosserial code: Unity. Its three suites use rosserial's node handle with a fake serial port, and only the environment native has the rosserial library. Their folders are test/test_<name>/, and native runs them. The suites of the BNO055 driver, the command timeout, the PID controller and the wheel control are Unity suites too. A Unity suite of the core moves to GoogleTest when its code changes.
    • A test that has to run on the Teensy itself: Unity. PlatformIO runs Unity on microcontrollers, and GoogleTest only on the PC and ESP boards (GoogleTest in PlatformIO). The firmware has no such suite yet. Its checks on the Teensy are sketches that you run by hand, such as test/encoders, and the commands on this page leave them out.

    GoogleTest is a C++ framework. Tests that share a setup put it into a fixture, and a test that has to run with several values is written once and runs once per value. A failure names the value. GoogleTest also finds the tests by itself, while a Unity suite lists each test by hand. Unity is a small framework written in C for microcontrollers (Unity in PlatformIO). Its checks are C macros, and the firmware's Unity suites are C++ files too. ROS uses GoogleTest for its C++ tests, in ROS 1 (gtest on the ROS wiki) and in ROS 2 (Writing Basic Tests with C++ with GTest).

    test/googletest holds one suite, test_wire_bus. It tests WireBusT (wire_bus.h), the adapter that carries out the BNO055 driver's I2C transfers with Arduino's Wire library (How the firmware reads it on the IMU page). WireBusT takes the Wire library's class as a template argument. On the Teensy that is Arduino's TwoWire. The suite passes its fake, FakeWire, so the adapter builds and runs on the PC too.

    How PlatformIO keeps the suites apart

    One environment builds its suites with one framework. So the firmware has an environment for each framework, and each suite's folder decides which environment runs it:

    graph TB subgraph ENVIRONMENTS [platformio.ini: environments] NATIVE[native:<br/>Unity] GOOGLETEST[native_googletest:<br/>GoogleTest] end subgraph SUITES [suites] UNITY_SUITES[test/test_bno055,<br/>test/test_pid, ...] GOOGLETEST_SUITES[test/googletest/<br/>test_wire_bus] end NATIVE -->|builds and runs| UNITY_SUITES GOOGLETEST -->|builds and runs| GOOGLETEST_SUITES

    PlatformIO takes every folder below test whose name starts with test_ as a PlatformIO test suite, and names the suite by its path: test_pid, or googletest/test_wire_bus (Test Hierarchy). The settings test_filter and test_ignore of platformio.ini compare patterns with that path:

    • The section [env]: sets test_ignore = googletest/*. Its options hold for every environment that doesn't set them itself (Common [env]). So the two Teensy environments and native ignore every suite below test/googletest.
    • native: test_framework = unity, and test_filter lists its Unity suites by name.
    • native_googletest: test_framework = googletest, test_filter = googletest/*, and its own test_ignore = test_*, which matches the Unity suites. A new GoogleTest suite needs no change of the file.

    A --filter on the command line replaces the environment's test_filter, but not its test_ignore. So a call that names a suite for the wrong environment builds nothing with the wrong framework: pio test -e native --filter "googletest/*" runs no suite. PlatformIO then reports 0 test cases and no error. CI also checks the result: its unit test job fails when no test case of one of the two environments passed.

// The calls of Arduino's TwoWire that WireBusT makes, with results a test can choose. FakeWire
// records the calls that start, fill and end a transfer, in their order. available() and read()
// only hand out the received bytes
class FakeWire
{
public:
    std::vector<std::string> calls;  ///< such as beginTransmission(0x28), write(0x3D)
    std::deque<uint8_t> received;
    uint8_t end_result = 0;        ///< endTransmission(): 0 is success
    int reported_count = -1;       ///< requestFrom()'s result; -1: the requested length
    int delivered_count = -1;      ///< bytes really received; -1: the requested length

    void beginTransmission(uint8_t address) { calls.push_back(beginTransmissionCall(address)); }
    size_t write(uint8_t value)
    {
        calls.push_back(writeCall(value));
        return 1;
    }
    uint8_t endTransmission(bool stop = true)
    {
        calls.push_back(endTransmissionCall(stop));
        return end_result;
    }
    uint8_t requestFrom(uint8_t address, uint8_t length)
    {
        calls.push_back(requestFromCall(address, length));
        received.clear();
        int n = delivered_count < 0 ? length : delivered_count;
        for (int i = 0; i < n; ++i)
            received.push_back((uint8_t)(FIRST_DELIVERED_BYTE + i));
        return (uint8_t)(reported_count < 0 ? length : reported_count);
    }
    int available() { return (int)received.size(); }
    int read()
    {
        if (received.empty())
            return -1;
        int value = received.front();
        received.pop_front();
        return value;
    }
};

    One behavior with several inputs: a parameterized test

    A read can come back short in several ways, and readRegisters() has to fail for each of them. The BNO055 driver reads a sample's 18 data bytes in one transfer. readRegisters() asks Wire's requestFrom() for that requested length, and two counts come back:

    • Reported: the count that requestFrom() returns.
    • Arrived: the bytes that are really there, which available() tells.

    readRegisters() returns true only when both counts are the requested length. Otherwise it returns false, and it reads the bytes that arrived out of the Wire library, so that none of them is left for the next read. The table shows the successful read and the four short reads of the suite, each with 18 bytes requested, and what readRegisters() returns:

    Read Reported Arrived Returns
    A sample's data 18 18 true
    Both short 4 4 false
    Reported short, all bytes there 4 18 false
    Reported one short, all bytes there 17 18 false
    Reported in full, one byte missing 18 17 false

    After each of the five reads, no byte may be left in the Wire library. The successful read copies its 18 bytes into data, and a short read drains the bytes that arrived. The test ReadRegistersReturnsAllBytesOfASample checks that read and the 18 bytes in data. The four short reads are the cases of a parameterized test.     See each test fail once

    Break the behavior that one of your checks promises, on purpose, run the suite, read the failure, and undo the change. Then you know that the check can fail. For example, EXPECT_EQ(wire_.available(), 0) promises that a short read leaves no byte behind. Without the loop that drains the bytes in readRegisters(), all four short-read cases fail at that check. A change that breaks a different behavior can pass a test that is focused on one behavior. Another test of the suite has to catch that change.
