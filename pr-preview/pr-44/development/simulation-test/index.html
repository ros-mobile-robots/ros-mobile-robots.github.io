    Simulation Test

    diffbot_gazebo has a simulation test: it drives DiffBot and Remo in Gazebo and checks where they went. Both CI workflows run it on every pull request (diffbot#110).

    What it checks

    Each robot has a rostest file, sim_drive_diffbot.test and sim_drive_remo.test. Both include sim_drive.launch, which starts:

    • Gazebo without a GUI, on the empty world, with the robot from its URDF (diffbot_view.launch). Gazebo needs no display for this.
    • The controllers from diffbot_control.yaml, the same file the real robot uses (diffbot_control.launch, without the rqt_robot_steering window).

    Then two tests run:

    • publishtest checks that /diffbot/joint_states and /diffbot/mobile_base_controller/odom are published.
    • test_drive.py drives forward at 0.2 m/s for 3 s, then turns at 0.5 rad/s for 3 s. It checks each move twice: with the controller's odometry, and with the robot's true pose from Gazebo (/gazebo/model_states). Both must be in range, and they must agree.

    The true pose is what makes the test useful. The odometry is computed from the wheel joints and the controller's configuration, so it repeats some configuration mistakes: with the left and right wheel swapped, the robot turns right while the odometry reports a left turn. A wrong wheel radius makes odometry and true distance differ. A wrong joint name stops the controller, so no odometry is published. The test fails in all three cases. The durations are simulation time, so the expected distances don't depend on how fast the computer runs the simulation.

    Gazebo and ros_control

    ros_control isn't a node of its own. It's a set of C++ libraries, used inside the process that has access to the joints:

    • A hardware interface, a class derived from hardware_interface::RobotHW, gives the controllers each wheel joint's position and velocity and takes a velocity command for it. The controllers read and write these values directly, in the same process, not over topics. How the hardware interface gets the values from the robot and passes on the commands depends on the robot: in Gazebo it reads and sets the simulated joints, on DiffBot it uses ROS topics to talk to the Teensy.
    • A controller manager loads the controllers as plugins and updates them. The program that creates the hardware interface and the controller manager runs the loop: read the joints, update the controllers, write the commands.
    • The controllers publish the topics that the test checks. joint_state_controller copies the joint values to /diffbot/joint_states. mobile_base_controller, a diff_drive_controller, computes the odometry from the wheel joint positions, publishes it, and turns the velocities from cmd_vel into a velocity command for each wheel.

    The two tabs show where these parts run, in the simulation test and on the real robot. When you switch between them, the blue box stays the same: the controller manager with the two controllers, configured by diffbot_control.yaml. Only the hardware interface and what's below it change.

    Topic names are shortened in the figures: cmd_vel and odom are under /diffbot/mobile_base_controller/, joint_states, wheel_cmd_velocities and measured_joint_states under /diffbot/, and model_states under /gazebo/. controller_spawner isn't shown; it only asks the controller manager to load and start the two controllers.

    In the simulation

    All three parts run inside the Gazebo server. The robot's URDF loads the gazebo_ros_control plugin (robot.gazebo.xacro). The plugin creates the hardware interface, DefaultRobotHWSim, for the wheel joints that have a transmission in the URDF, and a controller manager. In each simulation step the plugin runs the loop: readSim(), the controller manager's update, writeSim(). So the controllers publish from the /gazebo node.

    model_states doesn't go through ros_control: Gazebo's own ROS interface publishes the true pose of every model.

    On the real robot

    The diffbot_base node takes Gazebo's place. It creates the hardware interface DiffBotHWInterface and a controller manager, and runs the loop itself: read(), update the controllers, write(). Its launch file loads the same diffbot_control.yaml and spawns the same two controllers. This hardware interface talks to the Teensy over ROS topics: it subscribes to measured_joint_states, the wheel angles and velocities that the Teensy publishes, and read() passes the latest values to the controllers. write() publishes the wheel velocity commands on wheel_cmd_velocities, and the Teensy's firmware runs a PID loop per wheel to reach them (Base Hardware Interface). The rosserial node relays both topics over USB.

    So the simulation test covers the robot model and the controller configuration that both share. It doesn't run diffbot_base, rosserial or the firmware. Tests for diffbot_base and the firmware without the robot are planned in diffbot#114. ROS Control, An overview explains ros_control in more detail.

    Code walkthrough

    The test consists of four files in diffbot_gazebo/test: a .test file for each robot, sim_drive.launch and test_drive.py. In the package's CMakeLists.txt, add_rostest registers each .test file, so catkin build --catkin-make-args run_tests runs it.

    test_drive.py

    test_drive.py is a Python unittest class that rostest.rosrun() runs as a ROS node.

    Setup: setUpClass runs once, before the tests. It starts the node, a publisher for cmd_vel, and subscribers for the odometry and /gazebo/model_states. The two callbacks keep only the latest pose of each, as x, y and heading θ (planar(); θ comes from the orientation quaternion, with euler_from_quaternion from tf). Then it waits up to 120 s for the first odometry, because Gazebo and the controllers start slowly in CI.

    Driving: drive() remembers both poses, sends the velocity command for the given time, then a zero command, and waits a second for the robot to stop:

    self.cmd_vel.publish(cmd)

self.cmd_vel.publish(Twist())
rospy.sleep(1.0)  # let the robot stop

    It sends the command 20 times a second because the controller stops the robot when no command arrives for 0.5 s (diff_drive_controller's default cmd_vel_timeout). rospy.Time and rospy.Rate follow Gazebo's clock (use_sim_time), so on a slow computer the test takes longer, but the robot drives the same distance. Then drive() returns the motion twice, once from the odometry and once from the true pose, each computed by relative_motion().

    Comparing the motions: the odometry and Gazebo give poses in different frames. The odometry starts at 0, 0, 0 where the controller started, while Gazebo spawns the robot at x = −2 m, y = −0.5 m in its world frame. So the test doesn't compare the poses, but the motion between them. It describes the motion as the odometry motion model in Probabilistic Robotics (affiliate link) by Thrun, Burgard and Fox, section 5.4, does: a rotation δrot1 towards the end position, a straight translation δtrans to it, and a rotation δrot2 to the end heading. These three numbers are the same in every frame.

    For the start pose (x₀, y₀, θ₀) and the end pose (x₁, y₁, θ₁), the book computes them as:

    \[ \begin{aligned} \delta_\text{rot1} &= \operatorname{atan2}(y_1 - y_0,\; x_1 - x_0) - \theta_0 \\ \delta_\text{trans} &= \sqrt{(x_1 - x_0)^2 + (y_1 - y_0)^2} \\ \delta_\text{rot2} &= \theta_1 - \theta_0 - \delta_\text{rot1} \end{aligned} \]

    The robot turned by δrot1 + δrot2 = θ₁ − θ₀ in total. Both angles are wrapped to −π to π, because θ jumps from π to −π when the robot turns past 180°. That would make a small left turn look like almost a full turn to the right. When the robot turns on the spot, its position hardly changes, and the direction of such a short translation is noise. So below 1 cm, δrot1 is 0 and δrot2 is the whole turn, as in the odometry model of ROS's amcl (amcl_odom.cpp). In Gazebo the robot's center still drifts 2 to 4 cm while it turns on the spot, so the turn test checks the total turn, not δrot1 and δrot2 on their own. In relative_motion() in test_drive.py:

    1
2
3
    trans = math.hypot(x1 - x0, y1 - y0)
rot1 = wrap(math.atan2(y1 - y0, x1 - x0) - theta0) if trans >= 0.01 else 0.0
rot2 = wrap(theta1 - theta0 - rot1)

    The models behind the numbers: the test itself doesn't model the robot; δrot1, δtrans and δrot2 only describe the motion between two poses. The models are elsewhere:

    • The commands follow the velocity motion model of the same book (section 5.3): constant linear and angular velocities v and ω. With ω = 0 the robot drives straight, v·t = 0.6 m; with v = 0 it turns on the spot, ω·t = 1.5 rad. These are the expected values.
    • The controller's odometry integrates the wheel motion with the kinematic model of a differential drive robot (Odometry).
    • Gazebo simulates the robot's URDF model with physics: mass, inertia, and the friction and slip of the wheels.

    The checks: test_forward drives at 0.2 m/s for 3 s, and test_turn turns on the spot at 0.5 rad/s for 3 s. Each checks the motion from the odometry and from the true pose:

    test_forward test_turn
    Range δtrans 0.4 to 0.75 m: 0.6 m commanded, a bit less with the controller's acceleration limit. Straight ahead: |δrot1| below 0.15 rad (0.002 rad measured), so the robot moved in the direction it faced, and the total turn below 0.2 rad Total turn 0.5 to 2.0 rad to the left: 1.5 rad commanded, but the wheels don't always reach the commanded speed when turning on the spot (Remo turned about 1.1 rad). δtrans below 0.15 m
    Odometry and true pose agree δtrans within 0.05 m. They're usually about 0.01 m apart; a wheel radius 20 % too big gave 0.09 m Total turn within 0.25 rad. The wheels slip a little (0.02 to 0.11 rad apart); a wheel radius 20 % too big gave up to 0.31 rad

    unittest runs the test methods in alphabetical order. Each test checks only its own motion, from wherever the robot is when it starts, so the order doesn't matter.

    Run it

    Run it in the dev container, in ~/catkin_ws: all tests with the two commands from the dev container workflow, or one robot:

    1
    rostest diffbot_gazebo sim_drive_diffbot.test

    With --text, rostest prints the nodes' output in the terminal instead of log files, but it doesn't collect the test results then: it can report success although a check failed. Use --text to watch a run, and the command without it to check the result.

    Add a check

    Add a test method to test_drive.py, a Python unittest class: call self.drive() and check the two motions it returns. It runs for both robots. A new .test file is registered with add_rostest in the package's CMakeLists.txt. Give it its own gazebo_port, like the two existing ones: catkin runs the test files in parallel, and two Gazebo servers on the same port can't start.
