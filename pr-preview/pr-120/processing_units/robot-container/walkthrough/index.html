    Code Walkthrough

    This page walks through the code of the robot container, file by file. You don't need the page to use the robot. The page is for reading the code, and for changing the code.

    The sections follow a reading order. The Dockerfile comes first, because the Dockerfile defines what the robot's Docker image contains. Then come the entrypoint script, compose.yaml and the udev rules, and last the workflow that builds, tests and publishes the image. The files act in another order, which the figure below shows.

    All files are in the diffbot repository, in the folder .docker/robot, except the workflow. The excerpts on this page show these files at one commit of the repository.

    From a change to the running robot

    The figure shows the order in which the files act, from top to bottom. The steps in the upper box run on GitHub's computers. The build and the test run for every change of the image or its packages. The publication runs on noetic-devel only, after such a change is merged or after a start by hand, when both architectures passed. The steps in the lower box happen on the robot's Raspberry Pi. The udev rules act when a device is plugged in. Compose reads compose.yaml and .env when you run docker compose. Docker runs the entrypoint script when a container starts.

    The Dockerfile

    Docker builds an image by running the instructions of a Dockerfile from top to bottom. The instructions that change files, such as RUN and COPY, each add a layer of files to the image. Others, such as ENV, LABEL and CMD, set values that the image carries along. Docker keeps each step's result in its build cache. A later build reuses a step's result when the step's instruction, the instruction's input files and all earlier steps are unchanged. The order of the instructions in Dockerfile follows from that: what changes seldom comes first, and the repository's code comes last.

    Stage 1: only the package.xml files

    The Dockerfile has two stages. A stage starts with FROM, and a later stage can copy files out of an earlier one. The first stage, named manifests, copies the repository into a throwaway image and keeps only the package.xml files, each in its package's folder.

    Dockerfile

    # Stage 1, named manifests (ROS calls a package.xml the package manifest): copy only the
# package.xml files out of the repository, as the dev container does. The step that installs
# the dependencies then reruns only when a package.xml changes, not on every code change.
FROM ubuntu:20.04 AS manifests
COPY . /src
RUN mkdir /manifests \
    && cd /src \
    && find . -name package.xml -exec cp --parents {} /manifests \;
    • COPY . /src (line 15): copies the build context into the stage. The build context is the repository's root folder, without what .dockerignore excludes.
    • find … -exec cp --parents (line 18): copies each package.xml to /manifests, with its folders. So diffbot_base/package.xml becomes /manifests/diffbot_base/package.xml.

    A package.xml lists the dependencies of a ROS package, and ROS calls this file the package's manifest. The second stage installs the dependencies from these files alone. So a change of the code alone doesn't rerun that slow step: Docker reuses the step's result from the build cache. The step runs again when a package.xml changed, or something before the step, such as the list of packages or the base image.

    The user ros

    The robot's processes don't run as root. The Dockerfile creates a user for these processes, with a user ID that the Dockerfile takes as a build argument.

    Dockerfile
    40

    # The user ros, with UID and GID 1000, the usual IDs of the first user on Linux, so that files it
# writes to a mounted host folder (logs, bags) belong to that user on the host. No sudo: the
# robot's processes don't need root.
ARG USERNAME=ros
ARG USER_UID=1000
ARG USER_GID=$USER_UID
RUN groupadd --gid $USER_GID $USERNAME \
    && useradd --uid $USER_UID --gid $USER_GID --create-home --shell /bin/bash $USERNAME
    • ARG USERNAME, USER_UID, USER_GID (lines 43–45): the user's name and IDs. ARG defines a value that exists only during the build. The defaults are ros and 1000.
    • groupadd and useradd (lines 46–47): create the group and the user with these IDs, and the home folder /home/ros.

    The ID 1000 matters for the logs. The containers write ROS's log files into a folder of the Raspberry Pi (ROS's log files). Linux decides by the ID, not by the name, who may write there. The first user on Ubuntu usually has the ID 1000 too, so the files belong to that user.

    Two packages of the list aren't in the diffbot repository: Remo's model remo_description and the lidar driver rplidar_ros. vcstool fetches their repositories into the workspace. A catkin workspace is a folder whose src folder holds the source code of ROS packages, which catkin builds together. The image's workspace is /home/ros/catkin_ws (the folders in the container).

    # Install the dependencies of the packages to build with rosdep, from their package.xml files:
# the diffbot packages from stage 1, the fetched repositories from src. The base image already
# set up rosdep. Then delete apt's package lists and the copied files.
USER root
COPY --from=manifests /manifests /tmp/manifests
RUN paths="src" \
    && for p in $PACKAGES; do if [ -d /tmp/manifests/$p ]; then paths="$paths /tmp/manifests/$p"; fi; done \
    && apt-get update \
    && rosdep install --from-paths $paths --ignore-src --rosdistro noetic -y \
    && rm -rf /var/lib/apt/lists/* /tmp/manifests
    • COPY --from=manifests (line 66): takes the package.xml files out of stage 1.
    • paths (lines 67–68): the folders that rosdep reads. The variable starts with src, where the fetched repositories are. The loop adds the folder of each package in PACKAGES that stage 1 has a package.xml for.
    • rosdep install (line 70): installs the dependencies. --ignore-src skips the packages that are in the folders themselves, because catkin builds those.
    • rm -rf (line 71): deletes apt's package lists and the copied files.

    rosdep gets the folder of each package, and not only the bringup's, because rosdep reads only the package.xml files that rosdep is given. In its package.xml, a package declares each other package that the package needs at run time with an <exec_depend> line, for example:

    diffbot_bringup/package.xml
    1
    <exec_depend>diffbot_base</exec_depend>

    With this line, rosdep would recognize diffbot_base as a package of the workspace. But rosdep wouldn't read the package.xml of diffbot_base, and so wouldn't install what diffbot_base needs, such as rosserial. That's the result of our test with rosdep 0.25.1 in the ROS image.

    • COPY --chown=$USERNAME . src/diffbot (line 76): copies the repository into the workspace's src folder, owned by the user ros.

    • catkin build … $PACKAGES (line 79): builds the packages of the list, and the workspace packages that these packages declare as dependencies. catkin does follow the <exec_depend> lines. Adding the missing lines is the first step of diffbot#131.

    The built packages stay in the workspace's devel folder. The containers load them from there (The entrypoint script).

    The entrypoint script

    entrypoint.sh is the program that Docker starts in every container of the image, as the Dockerfile's ENTRYPOINT line says (What a container runs). The script loads ROS, and then hands over to the command that the script got as its arguments.

    Who starts the script

    The figure shows the two ways in which the script gets started. On the left, Docker starts the script with a new container. On the right, a person names the script in a command.

    graph TB UP[docker compose up<br/>-d --no-build] DS[Docker starts<br/>the container] E1[entrypoint.sh, with the<br/>service's command<br/>as its arguments] RL[roslaunch: the container's<br/>main process] N[the nodes of<br/>the launch file] EX[docker compose exec bringup<br/>/entrypoint.sh rostopic list] E2[entrypoint.sh, with<br/>rostopic list<br/>as its arguments] RT[rostopic list: one more<br/>process in the container] UP --> DS DS -->|runs| E1 E1 -->|exec| RL RL -->|starts| N EX -->|runs| E2 E2 -->|exec| RT
    • When a container starts: Docker runs the script and passes the container's command as the script's arguments. The command is the service's command line in compose.yaml, for example roslaunch diffbot_bringup bringup.launch model:=remo.
    • When a command names the script: docker compose exec adds one more process to a running container. Docker doesn't run the ENTRYPOINT for such a process. So the command line names the script itself, in front of the ROS command (On the robot alone).

    #!/bin/bash
# Entry point of the robot image: load ROS and the robot's workspace, then run the command,
# by default the bringup (Dockerfile's CMD, or the command in compose.yaml).
set -e

# ROS reads ROS_IP and ROS_HOSTNAME when they are set, even to an empty string, and roscpp
# rejects an empty one. compose.yaml passes them through, so remove them when they are empty.
[ -n "$ROS_IP" ] || unset ROS_IP
[ -n "$ROS_HOSTNAME" ] || unset ROS_HOSTNAME

source /opt/ros/noetic/setup.bash
source "$HOME/catkin_ws/devel/setup.bash"
# "$@" is the command that this script got: compose.yaml's command, the Dockerfile's CMD, the
# rest of a docker run line, or what follows /entrypoint.sh when docker exec runs it explicitly.
# exec runs it in place of this script, in the same process. For the container's main process,
# that means the command gets Docker's stop signal itself and can shut its nodes down cleanly.
exec "$@"
    • set -e (line 4): the script stops at the first command that fails, for example when a file to load is missing.
    • [ -n "$ROS_IP" ] || unset ROS_IP (lines 8–9): the two lines check ROS_IP and ROS_HOSTNAME separately. Each line unsets its variable if the value is empty. That happens with a line such as ROS_IP= in .env. The comment above the two lines gives the reason: ROS reads these variables also when they are empty, and ROS's C++ nodes reject an empty one.
    • source /opt/ros/noetic/setup.bash (line 11): loads the ROS installation. Afterwards the shell finds ROS's programs, such as roslaunch and rostopic, and ROS_MASTER_URI has its default, http://localhost:11311, if nothing has set the variable.
    • source "$HOME/catkin_ws/devel/setup.bash" (line 12): adds the workspace on top, so that ROS finds the robot's packages that the Dockerfile built (Build the workspace).
    • exec "$@" (line 17): "$@" stands for all arguments of the script, which are the command to run. exec runs that command in place of the script, in the same process. So the script leaves no shell behind: roslaunch becomes the container's main process. When Docker stops the container, roslaunch gets the stop signal itself and can shut its nodes down.

    # Settings that both services share (a YAML anchor)
x-robot: &robot
  # The image that CI published for noetic-devel, unless .env sets ROBOT_IMAGE. Without --no-build,
  # Compose builds it from this repository when the download fails (bringup's build section).
  image: ${ROBOT_IMAGE:-ghcr.io/ros-mobile-robots/diffbot-robot:noetic}
  # The host's network, so that ROS reaches the PC as in the native setup, without port lists
  network_mode: host
  # Let the user ros in the container open the serial devices: add the numeric ID of the group
  # that owns them on the host. A group name could have a different ID in the container.
  group_add:
    - "${DIALOUT_GID:-20}"
  environment:
    - ROS_MASTER_URI
    - ROS_IP
    - ROS_HOSTNAME
  # ROS logs and bags in a host folder. The long syntax doesn't create a missing folder: Docker
  # would create it for root, and the user ros couldn't write its logs.
  volumes:
    - type: bind
      source: ${ROBOT_DATA:-${HOME}/robot-data}
      target: /home/ros/.ros
      bind:
        create_host_path: false
  # The containers' output (docker compose logs) in Docker's local log format. By default it keeps
  # 5 files of 20 MB per container and deletes the oldest, so it can't fill the SD card. Docker's
  # default format, json-file, keeps everything unless rotation is configured.
  logging:
    driver: local
    • image (line 25): the Docker image from the setting ROBOT_IMAGE, or the published one. Compose writes ${NAME:-default} for a setting with a default.
    • network_mode: host (line 27): the containers use the Raspberry Pi's network directly, so their ROS nodes are reachable at the Raspberry Pi's IP address, like native ones. ROS 1 needs this: besides the ROS master's port 11311, every node opens a random port of its own, and the other nodes connect to that port directly (ROS Network Setup).
    • group_add (lines 30–31): adds the group with the number from DIALOUT_GID to the container's user, so that the user ros may open the serial devices (Why DIALOUT_GID is a number).
    • environment (lines 32–35): the environment variables inside the containers. ROS_MASTER_URI, ROS_IP and ROS_HOSTNAME are listed without a value: Compose takes their values from .env, or from the shell, when Compose creates the containers. A variable that's set in neither isn't set in the containers either (environment in Compose's reference).
    • volumes (lines 38–43): mounts the Raspberry Pi's folder for logs at /home/ros/.ros inside the containers, where ROS writes its log files (ROS's log files). create_host_path: false keeps Docker from creating a missing folder: Docker would create the folder for root, and the user ros couldn't write into such a folder.
    • logging (lines 47–48): Docker's local log format. By default, this format keeps at most five files of 20 MB per container and deletes the oldest, so the containers' output can't fill the SD card. Docker's default format, json-file, keeps everything unless rotation is configured.

    The udev rules

    99-diffbot-robot.rules is installed in the Raspberry Pi's own operating system. udev is the service of the Raspberry Pi's Linux that creates the device files in /dev (udev's manual page). udev reads these rules outside the robot's containers. The rules make udev give the Teensy and the lidar a name that stays the same. Stable device names on the setup page installs the file.

    # udev rules for the robot's host OS, not for the container: stable names for the Teensy and the
# lidar, which compose.yaml passes into the container. Without them, the kernel numbers serial
# devices in the order they appear, so /dev/ttyACM0 or /dev/ttyUSB0 can change.
# Install on the host:
#   sudo cp 99-diffbot-robot.rules /etc/udev/rules.d/
#   sudo udevadm control --reload-rules && sudo udevadm trigger
# Then /dev/teensy and /dev/rplidar link to the devices. If the robot has two devices with the
# same IDs, tell them apart with ATTRS{serial}=="..." (shown by: udevadm info -a /dev/ttyACM0).

# Teensy 4.0 and 3.2 in USB serial mode: PJRC's vendor ID 16c0, product 0483
SUBSYSTEM=="tty", ATTRS{idVendor}=="16c0", ATTRS{idProduct}=="0483", SYMLINK+="teensy"

# RPLidar A1/A2: its USB adapter, a Silicon Labs CP210x (10c4:ea60)
SUBSYSTEM=="tty", ATTRS{idVendor}=="10c4", ATTRS{idProduct}=="ea60", SYMLINK+="rplidar"

    A rule is a list of parts with commas between them. A part with == is a condition. A part with += says what udev does for a device that meets all conditions of the rule. The parts of the two rules:

    • SUBSYSTEM=="tty" (lines 11 and 14): the device is a serial device. The kernel names such devices ttyACM0, ttyUSB0 and so on, in the order in which the devices appear.
    • ATTRS{idVendor} (lines 11 and 14): the USB vendor ID. ATTRS looks at the device and at the devices above it, and the IDs belong to the USB device, which is above the serial device. Both ATTRS conditions of a rule have to hold for the same device. 16c0 is the vendor ID of the Teensy, 10c4 the vendor ID of the lidar's USB adapter.
    • ATTRS{idProduct} (lines 11 and 14): the USB product ID. 0483 is the Teensy in USB serial mode, ea60 the lidar's USB adapter.
    • SYMLINK+= (lines 11 and 14): udev adds a link with this name in /dev, next to the kernel's name. That gives /dev/teensy in the first rule and /dev/rplidar in the second.

    What follows from the rules:

    • The result: a serial device with the IDs of line 11 is reachable as /dev/teensy, whatever number the kernel gave the device. compose.yaml names the device by this link and passes the device into the bringup container (The two services).
    • Two devices with the same IDs: both would match the same rule. The comment in lines 7–8 names the way out: one more condition, ATTRS{serial}, with the device's serial number.

    robot_container.yml is the GitHub Actions workflow of the robot's Docker image. The workflow builds the image, tests the image and, on noetic-devel, publishes the image.   if [ -z "$current" ]; then
    fail "$image:noetic has no commit annotation"
  elif [ "$current" = "$commit" ]; then
    if [ "$(digest_of "$image:noetic")" != "$index" ]; then
      fail "$image:noetic has the commit $commit, but not the digest $index"
    fi
    echo "$image:noetic is $version already"
  elif git merge-base --is-ancestor "$current" "$commit"; then
    promote
  elif git merge-base --is-ancestor "$commit" "$current"; then
    echo "$image:noetic stays at the later commit $current"
  else
    fail "$image:noetic has the commit $current, which isn't before or after $commit in git history"
  fi
else
  promote
fi
    • promote (lines 152–158): points noetic to the version and checks that noetic then has the version's digest.
    • noetic doesn't exist yet (lines 176–177): promote.
    • noetic is at this commit already (lines 164–168): nothing to write. The digests have to be equal.
    • noetic is at an earlier commit (lines 169–170): promote. git merge-base --is-ancestor tells whether one commit comes before another in the history.
    • noetic is at a later commit (lines 171–172): noetic stays where it is.
    • Neither before nor after, or no commit noted at noetic (lines 162–163 and 173–174): the script stops.
