    Firmware Container

    The Teensy firmware in diffbot_firmware builds with PlatformIO, which isn't in the dev container. The dev container can't run the current Teensy tools either: its Ubuntu 20.04 has glibc 2.31, the C library, and the PlatformIO Teensy tools need 2.34 or later. In our test, the tool teensy_size stopped there with a missing GLIBC_2.34.

    So the firmware has a container of its own, .docker/firmware: Debian 12 with glibc 2.36, Python 3.12, PlatformIO 6.2.0 and a compiler, without ROS. A script runs PlatformIO in it as your user, and CI builds the firmware the same way. You need only Docker.

    Use it

    In a terminal on your PC, in your diffbot clone's root folder. On Windows, that's the Ubuntu of WSL 2, not the dev container:

    1
2
    .docker/firmware/pio run -e teensy40
.docker/firmware/pio run -e teensy31

    pio is PlatformIO's command, and -e selects one of the boards in platformio.ini: teensy40 builds for the Teensy 4.0, teensy31 for the Teensy 3.1/3.2. Without -e, pio run builds teensy40. The first build downloads the base image, PlatformIO and the Teensy toolchain, which needs the internet and took about a minute on our test PC. Later builds take seconds.     The firmware file is then diffbot_firmware/.pio/build/<board>/firmware.hex, and it belongs to you. PJRC's Teensy Loader flashes it onto the Teensy. Don't build in the container and on the PC at the same time, because both write to diffbot_firmware/.pio.

    Another user and group ID: the script uses yours (id -u and id -g) unless you set LOCAL_UID and LOCAL_GID, for example LOCAL_UID=1234 LOCAL_GID=1234 .docker/firmware/pio run -e teensy40. That ID needs write access to your clone. In the container, id then shows:

    How it works

    The excerpts show the files at the diffbot commit that this page pins, with their line numbers. The link above each block opens the same lines on GitHub.

    The script

    .docker/firmware/pio runs from anywhere, because it finds compose.yaml next to itself. It first sets the IDs, lines 13–16:

    pio: the IDs
    13
14

16
    here="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
export LOCAL_UID="${LOCAL_UID:-$(id -u)}"
export LOCAL_GID="${LOCAL_GID:-$(id -g)}"
compose=(docker compose -f "$here/compose.yaml")

    ${LOCAL_UID:-$(id -u)} keeps a LOCAL_UID that you set, and takes your user ID otherwise. export passes both to Docker Compose. compose holds the start of every Compose command, with the path to compose.yaml.

    Then it builds the image, lines 18–31:

    # The first build shows its progress, because it downloads the base image and packages. Later
# builds take seconds, because Docker reuses the cached image layers whose inputs haven't changed.
# Their output only shows when they fail.
image="$("${compose[@]}" config --images firmware)"
if ! docker image inspect "$image" > /dev/null 2>&1; then
    "${compose[@]}" build firmware
else
    status=0
    build_log="$("${compose[@]}" --progress plain build firmware 2>&1)" || status=$?
    if [ "$status" -ne 0 ]; then
        printf '%s\n' "$build_log" >&2
        exit "$status"
    fi
fi

    config --images asks Compose for the image's name, which contains your IDs. When that image doesn't exist yet, the build shows Docker's progress, because it downloads for a while. Otherwise the build takes seconds when the Dockerfile and requirements.txt haven't changed, because Docker reuses its cached layers. The script keeps the build's output and prints it only when the build fails.

    Last, it runs PlatformIO in the container, lines 33–38:

tty_flag=()

    tty_flag=(-T)
fi
exec "${compose[@]}" run --rm ${tty_flag[@]+"${tty_flag[@]}"} firmware pio "$@"

    run --rm starts a container for this one command and removes it afterwards. pio "$@" passes your arguments on, for example run -e teensy40. Without a terminal, in CI for example, -T starts the container without one. exec replaces the script with Docker, so the build's exit code is the script's.

      args:

    image: diffbot-firmware-build:pio-6.2.0-${LOCAL_UID}-${LOCAL_GID}
    user: "${LOCAL_UID}:${LOCAL_GID}"
    volumes:
      # The whole repository, so that PlatformIO finds the project in diffbot_firmware
      - ../..:/workspace
      # Where PlatformIO keeps its downloads (platforms, toolchains, frameworks): /pio-core in the
      # container. Without PIO_CORE, that's the Docker volume pio-core below, which keeps them
      # between runs on your PC. With PIO_CORE set to a folder, it's that folder instead. CI does
      # that, because each CI job starts on a fresh machine: it saves the folder in its cache.
      - ${PIO_CORE:-pio-core}:/pio-core
    working_dir: /workspace/diffbot_firmware

volumes:
  pio-core:
    name: diffbot-firmware-pio-core-${LOCAL_UID}-${LOCAL_GID}
    • build: the image is built from the Dockerfile in this folder, with your IDs as build arguments. ${LOCAL_UID:?…} stops with that message when LOCAL_UID isn't set.
    • image: the image's name carries your IDs, so another user on the same PC gets an image of their own.
    • user: the container runs with your IDs, so the files it writes into the repository belong to you.
    • volumes: the whole repository is mounted at /workspace, and the container starts in diffbot_firmware. PlatformIO keeps its downloads in /pio-core: on your PC that's a Docker volume, a storage area that Docker keeps between runs, again with your IDs in its name. With PIO_CORE set to a folder, that folder is mounted there instead, which CI uses.

    # A user with your user and group ID, so that the build's files in the mounted repository belong
# to you. compose.yaml passes them as build arguments, from LOCAL_UID and LOCAL_GID, which the pio
# script sets to `id -u` and `id -g`. They have no default, so a build without both stops instead
# of silently using 1000. The user's home and the core folder belong to it, so a new volume
# mounted at /pio-core is writable too.
ARG USER_UID
ARG USER_GID
RUN if [ -z "$USER_UID" ] || [ -z "$USER_GID" ]; then \
        echo "USER_UID and USER_GID are missing: build through compose.yaml or the pio script" >&2; \
        exit 1; \
    fi
RUN (getent group "$USER_GID" || groupadd --gid "$USER_GID" pio) \
    && useradd --non-unique --uid "$USER_UID" --gid "$USER_GID" --create-home pio \
    && mkdir /pio-core \
    && chown "$USER_UID:$USER_GID" /pio-core
ENV PLATFORMIO_CORE_DIR=/pio-core
USER pio
WORKDIR /workspace/diffbot_firmware

    USER_UID and USER_GID have no default. A build without both stops instead of silently using 1000.

    Your user ID, and the other containers

    The ID travels in four steps: the script takes id -u, Compose passes it to the build as USER_UID, the Dockerfile creates the user pio with it, and the container runs as that ID. Files that the build writes into your clone, such as firmware.hex, then belong to you, not to root or another ID.

    The other containers solve the same problem differently:

    • The dev container creates its user ros with 1000, the usual ID of the first user on Linux. VS Code changes that user to your IDs when it creates the container (updateRemoteUserUID, on by default on Linux). The firmware container runs without VS Code, so it gets your IDs at build time instead.
    • The robot container runs as ros with 1000 on the Raspberry Pi, the robot's first user. The planned published image (diffbot#151) is built once per architecture with the IDs 1000, not for each robot's user. Setup covers a robot whose first user has another ID.

    - uses: actions/checkout@v7
# The build runs in the firmware image (.docker/firmware), through the same script as a local
# build, so CI uses the same pinned PlatformIO. The script sets LOCAL_UID and LOCAL_GID to
# the runner's user.
# PIO_CORE is a folder for PlatformIO's downloads in $RUNNER_TEMP, the runner's temporary
# folder, emptied at the start and end of each job (GitHub's default environment
# variables). A line NAME=value written to the file that $GITHUB_ENV names becomes an
# environment variable in every later step of this job (GitHub's workflow commands,
# "Setting an environment variable"). runner.temp below is the same folder.
- name: Settings for the firmware container
  run: |
    echo "PIO_CORE=$RUNNER_TEMP/pio-core" >> "$GITHUB_ENV"
    mkdir -p "$RUNNER_TEMP/pio-core"
# Each job starts on a fresh machine, so PlatformIO would download the Teensy toolchain every
# time. actions/cache restores the PIO_CORE folder from an earlier run and saves it after the
# job. compose.yaml mounts that folder as the container's /pio-core. One cache per board, so
# the two jobs don't write the same one.
- uses: actions/cache@v6
  with:
    path: ${{ runner.temp }}/pio-core
    key: pio-core-${{ runner.os }}-${{ runner.arch }}-${{ matrix.env }}-${{ hashFiles('.docker/firmware/requirements.txt', 'diffbot_firmware/platformio.ini') }}
    restore-keys: |
      pio-core-${{ runner.os }}-${{ runner.arch }}-${{ matrix.env }}-
- name: Build the firmware
  run: .docker/firmware/pio run -e ${{ matrix.env }}

    Each CI job starts on a fresh machine, where a Docker volume would be empty. So the first step sets PIO_CORE to a folder in $RUNNER_TEMP, the runner's temporary folder, and a line NAME=value in the file that $GITHUB_ENV names makes it an environment variable for the later steps (environment files). actions/cache restores a matching cache from an earlier run, if there is one, and saves a new one after a successful job when no cache had the exact key. The key holds the board, the runner's OS and architecture, and a hash of requirements.txt and platformio.ini. The script then sets the IDs to the runner's user, as on your PC.
