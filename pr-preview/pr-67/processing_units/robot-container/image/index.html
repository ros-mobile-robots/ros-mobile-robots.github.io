    Image and Tests

    The robot container runs ROS Noetic and the robot's packages on the Raspberry Pi from one Docker image, which CI builds and the Raspberry Pi downloads. This page explains how the image is built, what takes its space, and how CI tests and publishes the image. You don't need the page to use the robot container. The page is for changing the image, or for understanding the image.

    The page follows the image's way: how it's built, what takes the space, how it's tested and how it's published.

    How the image is built

    The robot's Docker image is defined in the diffbot repository's .docker/robot folder. Its Dockerfile starts from the official ROS image ros:noetic-ros-base, which exists for arm64 and amd64. It then adds the robot's packages in three steps, with the same tools as a native workspace:

    1. vcstool fetches the repositories listed in remo_robot.repos: Remo's model remo_description and the lidar driver rplidar_ros.
    2. rosdep installs the Ubuntu and ROS packages that the packages' package.xml files declare as dependencies.
    3. catkin builds the packages, in the workspace /home/ros/catkin_ws.

    A catkin workspace is a folder whose src folder holds the source code of ROS packages, which catkin builds together. The image has one, with the diffbot repository and the two fetched repositories in src (folders in the container). The dev container on your PC has its own.

    Which packages are built is a list in the Dockerfile (lines 58–61): the packages that the bringup and the lidar need, for both robots.

    Dockerfile
    58

    # The packages to build: the ones that the bringup and the lidar need, for both robots (the image
# has DiffBot's and Remo's models); diffbot_gazebo, the navigation and SLAM packages stay out.

ENV DIFFBOT_PACKAGES=$PACKAGES

    The list is needed because rosdep reads only the package.xml files it's given. In its package.xml, a package declares each other package it needs when the robot runs with an <exec_depend> line, for example:

    diffbot_bringup/package.xml
    1
    <exec_depend>diffbot_base</exec_depend>

    With this line, rosdep would recognize diffbot_base as a package of the workspace. But it wouldn't read diffbot_base's own package.xml, so it wouldn't install what diffbot_base needs, such as rosserial (our test with rosdep 0.25.1 in the ROS image). That's why rosdep gets the package.xml of each package to build.

    catkin does follow these lines: catkin build diffbot_bringup would first build the workspace packages that diffbot_bringup declares. But today diffbot_bringup declares only teleop_twist_keyboard, not the packages its launch files start. Adding them is the first step of diffbot#131. Gazebo, navigation and SLAM aren't in the image: they run on the PC.

    CI builds the image and publishes it (How it's published). Docker builds it on the Raspberry Pi only for your own build. The container runs as the user ros with UID 1000, not as root. The image also sets PYTHONUNBUFFERED and ROSCONSOLE_STDOUT_LINE_BUFFERED, so that Python and ROS write each line of output at once. Without a terminal, they would collect it first, and docker compose logs would show it late.

    The same inputs for both builds

    CI builds the image twice, once per processor architecture, on two computers (How it's tested). Three inputs of the build come from outside the diffbot repository. Two of them are named by their content, so both builds get the same files, also when one of the two builds runs again later. The third is named by a release tag:

    Remo's model remo_description By the release tag 2.5.0. A tag is a name for a commit. It selects one version, but it isn't a checksum of the content remo_robot.repos

    What takes the space

    Unpacked, the image takes about 3.2 GB on an amd64 PC, and about 0.7 GB compressed. On that PC, docker images shows about 3.9 GB, because Docker's containerd image store keeps both (disk space usage). That's the default for Docker Engine 29 and later on a fresh installation. Installations with the legacy image store keep only the unpacked files. It hasn't been measured on the Raspberry Pi yet. What takes the space, measured with du and dpkg-query in the image:

    • The official ROS image, 2.4 GB: besides ROS, it has the tools to build ROS packages, such as the C++ compiler, CMake and Boost's headers. 1.2 GB of it is a Fortran compiler, flang, with the compiler libraries it's built on (LLVM). It comes in through Boost: ROS's pluginlib depends on all of Boost. That includes Boost.MPI, for programs that run on several computers at once, which needs OpenMPI, and OpenMPI's development package needs a Fortran compiler.
    • The robot's part, about 0.7 GB of the unpacked 3.2 GB: almost all of it comes with RViz, which the robot models declare (Limitations): graphics drivers (Mesa), the window toolkit Qt and the 3D engine OGRE. The built workspace itself is about 70 MB.

    How it's tested

    The workflow robot_container.yml runs in three cases:

    • For a pull request: when the pull request changes the image or its packages.
    • For a push to the branch noetic-devel: when the push changes them. A merged pull request is such a push.
    • By hand: from the repository's Actions tab.

    The figure shows what a run does, and where a pull request's run ends:

    graph TB subgraph BUILD [Job build, once per architecture] PRE[Checks before the build:<br/>settings, local build name,<br/>publish script] IMG[Build the image] SMOKE[Smoke test, directly<br/>and through Compose] PRE --> IMG IMG --> SMOKE end PR[Pull request:<br/>passed or failed,<br/>nothing is kept] SAVE[noetic-devel:<br/>save the tested<br/>image as an archive] PUB[Job publish:<br/>copy both archives<br/>to the registry] SMOKE --> PR SMOKE --> SAVE SAVE --> PUB

    GitHub provides the computers that the workflow runs on, called runners. The job build runs twice: on an arm64 runner (ubuntu-24.04-arm, free for public repositories) and on an amd64 runner. These lines of the workflow name the two runners (lines 62–72):

    The Raspberry Pi's build was measured on 31 October 2026, at the diffbot repository's commit 3541965 (the bench record).

    Each run of the job build does five things, in this order:

    1. It checks the settings template: env.example has to give a valid configuration with compose.yaml.
    2. It checks the name of a local build: with ROBOT_IMAGE set to the published image's name and every service switched on, compose.yaml alone must build nothing, and compose.build.yaml must build only diffbot-robot:local, alone and combined with compose.yaml in both orders.
    3. It tests the publish script without a registry (The script's tests).
    4. It builds the image: with docker build, for the runner's own architecture.
    5. It runs smoke_test.sh in the image, twice: directly in a container of the image, and through compose.yaml with its mounts and groups.

    The smoke test checks four things, without hardware:

    • The packages and programs: ROS finds the packages, and the programs that talk to the hardware exist.
    • The robot models: both robots' URDF models expand with xacro.
    • The launch files: the bringup's and the lidar's launch files parse. The lidar's launch file names the driver's node /diffbot/rplidarNode, in the robot's namespace, so a connected lidar's scans are on /diffbot/scan.
    • Remo's bringup: the bringup starts, its URDF model loads, and both controllers run.

    The test doesn't start the lidar driver, and no check talks to a device. Without a Teensy, rosserial can't open its port and the hardware interface gets no wheel feedback, so the test can't show that the robot drives. That needs the real robot: the robot container's status says what ran on Remo and what is still open in diffbot#109.

    How it's published

    For a pull request, the run ends after the smoke tests. The result is the workflow's check, passed or failed, and the image is deleted with the runner. Nothing is published, because a pull request's code isn't reviewed yet.

    After a change is merged into noetic-devel, each run of the job build also saves the image that it tested, as an archive. A third job, publish, then copies both archives to the registry. It doesn't build the image again. So the published image is the very image that passed the smoke test, not a second build that could differ from it.     • The last step (lines 179–184): runs the script publish_image.sh with the image's name, the commit and the folder with the two archives. The job runs nothing from the images.

    The script copies both images to the registry and combines them under one name. A Raspberry Pi then downloads the arm64 image and a PC the amd64 one. The version noetic-<commit> is published once and never replaced, and noetic only moves to a later commit (Versions).

    What the script asks the registry first

    Before the script writes the version or noetic, it asks the registry about both names. For each name, the function state gives one of three answers, with the tool skopeo:

    Answer of state for one name What the registry said about that name
    present It returned the name's manifest, the description of an image. The name exists
    missing manifest unknown, the registry's own error code for a name that it doesn't have. The name is free
    unreadable The registry itself refuses: it denies the request for the name, it doesn't know the repository at all, or its token service answers 403
    No answer Anything else, after three tries: a failed login, a login file that can't be read, another error of the token service, no connection. The script stops and prints the error

    The script then decides from the two answers together:

    1. Both names are present or missing: the script publishes. It writes a name that is missing. A version that is present is checked and reused, never written again. A noetic that is present moves only to a later commit.
    2. One of the two names is unreadable: the script stops and writes nothing.
    3. Both names are unreadable, in a run for the first publication: the script copies one image under a name of its own and asks about both names again (The first publication). The version and noetic are still written only by rule 1.

    Only manifest unknown counts as "the name is free", because other failures read alike. A login helper that isn't installed and a token service that answers 404 both print not found, and neither says anything about the name. If the script took them for a free name, it could write a version that exists already. The same holds for unreadable: a login file that the job can't read prints permission denied, which is no answer of the registry.

    # What the registry says about a tag, <image>:<tag>:
#   present      The registry returned the tag's manifest.
#   missing      The registry answered the request for this tag's manifest with its error code
#                MANIFEST_UNKNOWN, which skopeo prints as "manifest unknown". Only this answer
#                counts. Other failures can read alike: a login helper that isn't installed and a
#                token service that answers 404 both print "not found", and neither says anything
#                about the tag.
#   unreadable   The registry itself refuses: it denies the request for this tag's manifest
#                (DENIED, UNAUTHORIZED), it doesn't know the repository (NAME_UNKNOWN), or its
#                token service answers 403. Each means that this job can't see the package,
#                which only the first publication may answer with a write (see below).
# Each answer is recognized by the text that skopeo prints for it, with this tag and repository
# in it. A text that skopeo words differently one day is none of them, and the job stops.
# A read that gives neither present nor missing is tried three times. After that, an error that
# is not unreadable stops the job: a failed login, a file that can't be read, an error of the
# token service or of the connection. The version and noetic are written only after both read
# as present or missing.
state() {
  local reference=$1 error="" refusal
  local repository=${reference%:*} tag=${reference##*:}
  local manifest_request="reading manifest $tag in $repository"
  local refusals=(
    "$manifest_request: denied"
    "$manifest_request: unauthorized"
    "$manifest_request: name unknown"
    "Requesting bearer token: invalid status code from registry 403 (Forbidden)"
  )
  for try in 1 2 3; do
    if [ "$try" -gt 1 ]; then
      sleep 15
    fi
    if error=$(skopeo inspect --raw "${read_options[@]}" "docker://$reference" 2>&1 >/dev/null); then
      echo present
      return
    fi
    if grep -q -F "$manifest_request: manifest unknown" <<<"$error"; then
      echo missing
      return
    fi
  done
  for refusal in "${refusals[@]}"; do
    if grep -q -F "$refusal" <<<"$error"; then
      echo unreadable
      return
    fi
  done
  echo "$error" >&2
  exit 1
}

    The function recognizes each answer by the text that skopeo prints for it, with the name's tag and repository in the text. The variable manifest_request holds the start of these texts, and the list refusals holds the registry's refusals.

    The script also checks that an archive holds the right architecture and commit before it copies that archive's image.

    The first publication

    The first publication is the one exception to "stops". The package doesn't exist yet then, and the registry may deny the read or say that it doesn't know the repository. A run for this case is one that a maintainer starts by hand, in the repository's Actions tab, with the box First publication ticked. If both names are unreadable in such a run, the script creates the package: it copies the checked amd64 image under the name first-publication, which nothing else uses, and asks about both names again. If the two answers still aren't present or missing, the script stops. So an image can be in the registry under first-publication although the run failed later, for example at the check of the arm64 archive. The version and noetic are not written in that case.

    The script's tests

    test_publish_image.sh runs publish_image.sh without a registry and without images. Stand-ins take the place of skopeo and docker. They answer the script's reads with texts recorded from skopeo, and they note each write that the script attempts instead of doing it. Each test chooses the registry's answer, runs the script, and compares the script's exit code and its writes with the expected ones:

    The registry's answer in the test Expected writes Expected result
    manifest unknown for both names Both images, the version and noetic The script succeeds
    A login helper that isn't installed None The script fails
    The token service answers 404 None The script fails
    A 404 page without the registry's error code None The script fails
    The registry can't be reached None The script fails
    The read is denied None The script fails
    The repository is unknown None The script fails
    The read is denied, in a first publication Only first-publication The script fails, because the read stays denied
    The repository is unknown, in a first publication Only first-publication The script fails, because the repository stays unknown
    The login file can't be read, in a first publication None The script fails
    One name is free and the read of the other is denied, in a first publication None The script fails
    The version and noetic exist None The script succeeds
    They exist, but one image is from another commit None The script fails
    They exist, but noetic has another digest None The script fails

    1
    .docker/robot/test_publish_image.sh

    The script prints one line per test, starting with ok or FAILED, and ends with the count:
