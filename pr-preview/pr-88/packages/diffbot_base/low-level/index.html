    DiffBot Base Package - Low Level Approach

    DiffBot Base introduces the two parts of the base controller. This page explains both: first the low-level firmware on the microcontroller (MCU), a Teensy, then the high-level hardware interface on the robot's computer.

    Implementing the low-level base controller for Remo

    Firmware excerpts

    The firmware excerpts on this page, the code blocks with a file name and line numbers, show the firmware at the diffbot commit that this page pins. The link before each excerpt opens the same lines on GitHub.

    A wheel command's way through the firmware

    The robot's computer sends the MCU wheel commands, about ten per second. Each command holds the target speed of each wheel, in rad/s. The firmware stores the targets, drives the motors toward them in a control step every 50 ms, and releases the motors when no new command comes. The figure follows one command that arrives when the MCU's clock shows 100 ms, with no command after it. The control period is 50 ms and the command timeout 1000 ms, as on the robot.

    graph TB T100["100 ms: a wheel command arrives<br/>targets stored,<br/>command timeout restarted"] T150["150 ms: control step<br/>read(): encoders and wheel states<br/>write(): PIDs and motors"] T200["200 ms, 250 ms, …<br/>a control step every 50 ms,<br/>with read() and write()"] T1100["1100 ms: the command is<br/>1000 ms old<br/>eStop(): motors released<br/>timeout warning logged<br/>read()"] T1150["1150 ms, …<br/>control steps with read() only"] T100 --> T150 T150 --> T200 T200 --> T1100 T1100 --> T1150

    The unit test test_wheel_control uses the same times in two of its tests, with a fake controller in place of the encoders and the motors. One test checks that the control step at 150 ms calls read() and then write(). The other checks that the step at 1100 ms calls eStop(), then the timeout log, then read(). No test steps through the control steps every 50 ms in between: the figure draws them as the loop runs them on schedule. On the robot, the first check at or after 1100 ms finds the expiry, which is later when a pass of the firmware's loop takes long.

    1. 100 ms, a command arrives: RosWheelCommandSubscriber receives the command and hands it to WheelControl::receiveCommand(). The two target speeds go to BaseController, and the command timeout starts again. Nothing drives the motors yet.
    2. 150 ms, a control step: loop() runs a control step every 50 ms. The step reads the encoders with read() and publishes the wheel states for the robot's computer. Then write() lets the two PIDs compute the motor outputs from the targets and sets the motors.
    3. From 200 ms on: the control steps repeat every 50 ms, with the same targets.
    4. 1100 ms, the command is 1000 ms old: WheelControl::step(), which loop() calls on every pass, finds that the command has expired. eStop() sets the targets and both motor outputs to zero, which releases the motors, and then the firmware logs the timeout. The unit test checks this order of calls: eStop log read.
    5. After that: the control steps only read and publish the wheel states. So the robot's computer keeps seeing the wheels' speeds while they coast to a stop. A new valid command lets the control steps drive again.

    On the robot, the hardware interface sends a command every 100 ms, also while the robot stands still, with zero speeds. A valid command holds exactly two finite wheel speeds, zeros included. Every valid command restarts the timeout when the firmware processes it. A message that the subscriber drops, for example one with a single speed, doesn't. So the timeout tells whether valid commands still reach the MCU, not whether the robot should move. On the robot, it expires when the commands stop, for example when the diffbot_base node stops.

    The next section compares this stop with a loss of power on the bench. The sections after it follow the same path through the code: the project and its libraries, how main.cpp connects the parts, the command timeout and the timing with the MCU's clock. The firmware's design comes last.

    Two kinds of stop

    A bench test on Remo's Teensy 4.0, with the wheels off the ground, shows how the command timeout differs from a loss of power (the bench results in diffbot#169):

    • The wheel commands stop: With the USB cable connected and the wheels driving, rosnode kill /diffbot/diffbot_base stopped the hardware interface, the node that sends the wheel commands. The firmware logged Wheel command timeout: motors stopped once, 0.92 s after the node stopped. The timeout counts from the last command that the firmware processed, and that command's time wasn't logged. With a command every 100 ms, the 0.92 s is consistent with a last command about 80 ms before the node stopped, but no log shows that arrival. The next debug sample showed a motor output of zero, and the wheels came to rest about 0.4 s after the warning.
    • The Teensy loses its power: On Remo, the Teensy gets its power over the USB cable from the Raspberry Pi, and the Teensy's 3.3 V supplies the logic of the motor driver. Pulling the USB cable while driving stopped the wheels at once (section 8 of the bench checklist). The motor driver lost its logic power together with the Teensy. The command timeout played no part in this stop.

    So pulling the Teensy's USB cable tests the power wiring, not the command timeout. To test the timeout, stop the node that sends the wheel commands and keep the Teensy powered.

    The firmware is a PlatformIO project in the diffbot_firmware folder of the diffbot repository. PlatformIO builds Arduino code for the Teensy and uploads it to the board.     Wire

    The firmware talks to the robot's computer with rosserial, drives the motors with Adafruit's Motor Shield V2 library and uses Wire for the I2C bus on pins 18 (SDA) and 19 (SCL), which the motor driver and the IMU share.

    diffbot_base_config.h holds Remo's settings, which the firmware is built with:

    • Encoder pins: the Teensy's pins for the encoders' Hall effect sensors, 5 and 6 for the left encoder, 7 and 8 for the right one.
    • Motor terminals: the Adafruit motor driver can drive four DC motors. For the cable routing, Remo uses terminals M4 and M3 for the left and the right motor.
    • PID: the gains of the two wheel PIDs, explained on PID Controllers.
    • Motor output range: PWM_MIN and PWM_MAX, −255 and 255.
    • Update rates: how often the control step and the debug output run, explained in Timing with the MCU's clock.
    • Command timeout: COMMAND_TIMEOUT_MS, how long the firmware drives the motors without a new wheel command.
    • IMU: the BNO055's address and the IMU publisher's settings in IMU_PUBLISHER_CONFIG, for example enabled false for a robot without an IMU.

    The figure shows what Remo's MCU connects to and over which wire. Trace the USB cable to the robot's computer, the I2C bus to the IMU and the motor driver, the motor driver's outputs to the motors, and the encoder signals back to the MCU's pins.

    The firmware's own libraries are in the lib folder:

    Library What it holds
    base_controller BaseController: the encoders, the two PIDs and the motor controllers, and the rosserial topics for the wheel states, the encoders' reset and the PIDs' gains
    motor_controller_interface MotorControllerIntf, the interface through which BaseController sets a motor's speed, whatever the motor driver
    motor_controllers AdafruitMotorController, that interface for the Adafruit FeatherWing, one object per motor

    ros_lib/diffbot_msgs holds the rosserial message headers of diffbot_msgs, such as WheelsCmdStamped.h, the message of the wheel commands that RosWheelCommandSubscriber receives.

    Connecting the firmware in main.cpp

    main.cpp creates the firmware's objects as globals, and their constructors connect them. setup() initializes them, and loop() runs the scheduled work. WheelControl gets its controller and its logger from these objects, and its times from its callers: the subscriber passes the MCU's time alongside each valid command, and loop() passes the time of each step. So the unit tests can put fakes in place of the controller and the logger, and pass their own times. In the order of the file:

    1. The node handle: other classes, such as BaseController, use the global ROS node handle to publish and subscribe. Its ros::NodeHandle::now() gives the ROS time for time stamps. Time intervals come from the MCU's own clock instead, as Timing with the MCU's clock explains. main.cpp creates the node handle in lines 20–22:

      AdafruitMotorController implements the abstract class MotorControllerIntf, whose setSpeed(int value) is all that BaseController calls to drive a motor. So another motor driver needs only another class that implements this interface. AdafruitMotorController reaches the motor driver through Adafruit's Adafruit_MotorShield class and gets one of its DC motors with getMotor(motor_num). AdafruitMotorController::setSpeed() turns a value from −255 to 255, the range of PWM_MIN and PWM_MAX, into a direction and a speed. Zero releases the motor.

    3. The base controller: BaseController holds most of the firmware's logic, line 29:

      BaseController is a template class. Its parameters are the motor controller's type, TMotorController, here AdafruitMotorController, and the motor driver's type, TMotorDriver, here Adafruit_MotorShield. Its constructor takes the node handle and the two motor controllers. It holds two diffbot::Encoder objects and two diffbot::PID controllers, which compute each motor's output from the difference between the target and the measured wheel speed.

    // wheel command to wheel_control.receiveCommand(), and loop() calls wheel_control.step()

      • ArduinoClock gives the MCU's clock, millis() and micros(), to the parts that need it. The unit tests replace it with a fake clock.
      • RosTimeoutLogger sends the timeout warning to the robot's computer with nh.logwarn(). WheelControl calls this logger after it has stopped the motors.
      • WHEEL_CONTROL_CONFIG holds the wheel control's two times: the command timeout, COMMAND_TIMEOUT_MS, and the control period, 50 ms at an UPDATE_RATE_CONTROL of 20 Hz. static_assert checks, when the firmware is compiled, that both times are longer than zero.
      • wheel_control, a WheelControl, gets the base controller, the times and the logger.
      • wheel_commands, a RosWheelCommandSubscriber, receives the wheel commands and passes each valid one on to wheel_control, with its arrival time from wheel_clock.

      decltype(base_controller) stands for the base controller's type, so that the long template type doesn't have to be written again. C++ creates these global objects in the order in which they appear in the file. So each object gets references only to objects that already exist: wheel_control to base_controller, and wheel_commands to wheel_control.

    void setup()
{
    // Register the wheel subscriber and the IMU publisher before topic negotiation, the handshake
    // between the Teensy and the robot's single-board computer (SBC):
    // 1. BaseController::setup() initializes the Teensy's node handle, registers the remaining
    //    topics and calls spinOnce() until the node handle reports a connection.
    // 2. On the SBC, serial_node.py opens the USB serial device and requests the Teensy's topic
    //    descriptions. serial_node.py is part of rosserial_python, not of this repository.
    // 3. spinOnce() handles that request and sends the registered publishers and subscribers.
    // 4. serial_node.py creates the corresponding ROS endpoints on the SBC. Its ROS subscriber
    //    forwards wheel commands to the Teensy, where spinOnce() dispatches the callback.
    // Registering a new topic later doesn't notify the SBC until another topic negotiation.
    // The two programs start independently. BaseController::init() also lets callbacks run
    // through spinOnce() while waiting for parameter replies.
    wheel_commands.subscribe(nh);
    imu_publisher.advertise();
    Wire.begin();
    base_controller.setup();
    base_controller.init();

    nh.loginfo("Initialize DiffBot Motor Controllers");
    motor_controller_left.begin();
    motor_controller_right.begin();
    nh.loginfo("Setup finished");
}

    wheel_commands.subscribe(nh) registers the wheel command subscriber. With the IMU enabled, imu_publisher.advertise() registers the imu/data_raw publisher. Both come before base_controller.setup(), which starts rosserial and calls spinOnce() while waiting for the robot's computer. When serial_node.py requests the firmware's topics over USB, spinOnce() answers with the publishers and subscribers registered so far. After sending that answer, rosserial marks the connection ready and base_controller.setup() can finish. The computer forwards wheel commands only for a subscriber in that answer. Wire.begin() starts the I2C bus for the motor driver and the IMU.

    Registering the subscriber before base_controller.setup() also matters for the command timeout. BaseController::setup() and init() already receive messages while they wait for the connection and read the parameters. Wheel commands that arrive then reach wheel_control already, as When a command is too old explains.

    The motor controllers' begin(uint16_t freq) has to be called in setup() itself, because MotorControllerIntf has no begin() or setup(). Such a function would tie the interface to motor drivers that need one.

    After setup(), loop() schedules the work at three configured intervals: the control step every 50 ms (UPDATE_RATE_CONTROL, 20 Hz), the debug output every 200 ms while debugging is on (UPDATE_RATE_DEBUG, 5 Hz), and with the IMU enabled a sampling slot every 20 ms, the period in IMU_PUBLISHER_CONFIG. The IMU publisher can publish a sample only when the BNO055 is ready and the rosserial node handle has synchronized its clock with the robot's computer. Each pass of loop() runs four parts, one after the other:

    1. loop() reads the MCU's clock, millis(), as now_ms and hands it to wheel_control.step().
    2. imu_publisher.update() gets no time reading from loop(). With the IMU enabled, it reads its own clock after wheel_control.step() has returned, a second reading in the same pass.
    3. publishDebugIfDue() gets the same now_ms as the wheel control's step.
    4. nh.spinOnce() handles the messages that have arrived over USB.

    // Use the Teensy's elapsed time for scheduling (see BaseController::LastUpdateTime).
    const uint32_t now_ms = millis();

    void step(uint32_t now_ms)
    {
        stopWhenCommandExpires(now_ms);
        if (now_ms - last_control_ms_ < control_period_ms_)
            return;

private:
    /// Checks the timeout on every call. On the first call that finds the last command
    /// expired, stops the motors and then logs, once
    void stopWhenCommandExpires(uint32_t now_ms)
    {
        const bool was_timed_out = timeout_.timedOut();
        timeout_.update(now_ms);
        if (!was_timed_out && timeout_.timedOut())
        {
            controller_.eStop();
            log_timeout_();
        }
    }

    The control step takes these steps at the control rate:

    1. BaseController::read() reads the encoders and publishes the wheel states for DiffBotHWInterface, on the measured_joint_states topic of message type sensor_msgs::JointState. step() calls read() also while the wheel commands are too old, so the robot's computer keeps getting the wheel states.
    2. In BaseController::write(), the PIDs compute the motor outputs from the speed error, the difference between the target and the measured wheel speed, and the motor controllers set the motors. The targets come from the last wheel command. step() calls write() only if the last command was new when the step began, that is, if timedOut() was false at the check before read().
    3. step() stores the current time in last_control_ms_, so that the next step comes one control period later.

    Before the control step, on every pass, stopWhenCommandExpires() checks the command timeout, also when no control step is due.

    template <class NodeHandle, class Clock>
void ImuPublisher<NodeHandle, Clock>::update()
{
    if (!config_.enabled)
        return;
    const uint32_t now_ms = Clock::millis();
    updateSensorLifecycle(now_ms);
    if (!takeSamplingSlot(now_ms))

    Because update() reads the clock after wheel_control.step() has returned, its now_ms is later than the now_ms of loop() when the wheel control's step took long, for example while a log message waited for the USB connection. With this reading, takeSamplingSlot() plans a sample every 20 ms, 50 times per second. The publisher reads a sample with readAndPublishSample() and publishes it on imu/data_raw only while the BNO055 is ready (Bno055::READY) and the clock is synchronized with the robot's computer (nh_.timeSynced()). A failed read isn't published, and neither is a sample whose read took longer than its time budget, 10 ms. The budget is checked after the read, so a slow read still makes the pass longer. publishDebugIfDue() then logs when debugging is on, with the now_ms of loop(). Finally, nh.spinOnce() reads the serial data that has arrived and calls the matching subscriber's callback when it decodes a valid message for a subscribed topic, for example the wheel commands' callback. nh.spinOnce() comes last, after the wheel control's step, for a reason that When the counters wrap explains.

    The command timeout

    When the robot's computer stops sending wheel commands while the MCU keeps running, the firmware stops the motors. That happens, for example, when the diffbot_base node stops. The hardware interface on the robot's computer publishes the wheel commands in DiffBotHWInterface::write(), once per pass of its control loop. That loop aims at 10 passes per second (ros::Rate rate(10.0)), and it sends commands also while the robot stands, with zero speeds. COMMAND_TIMEOUT_MS is 1000 ms in diffbot_base_config.h, so the firmware stops after about ten missed commands.

    • The timeout: update() times out once the last command is timeout_ms_ old, 1000 ms on the robot. From then on, CommandTimeout stays timed out until the next command arrives. update() doesn't stop anything itself. It only changes what timedOut() answers.
    • The start: CommandTimeout starts timed out (timed_out_ is true), so the motors aren't driven before the first command arrives.

    WheelControl acts on the moment when that answer changes. On every pass, step() first calls stopWhenCommandExpires(), in the step excerpt above. stopWhenCommandExpires() notes what timedOut() answers, calls update() and asks again. Only on the first pass that finds the command expired, when the answer changes from false to true, stopWhenCommandExpires() stops the motors with eStop() and then logs the timeout. So the motors are stopped and the timeout is logged once per timeout, not on every pass. A delayed loop can find the expiry later than the deadline. The private stopWhenCommandExpires() keeps the timeout's stop and log together, in that order.

    • Before the first command: timedOut() is true before and after update(). So nothing is stopped and no warning is logged. step() only reads the wheel states.
    • Commands during the setup: rosserial processes commands while base_controller.init() waits for the parameters' replies. The first control step runs after the motor controllers are initialized and checks the age of the last valid command like any later step. If that command has expired, the first step releases the motors and logs the timeout before either PID computes a motor output, even if the motors haven't been driven yet. With commands arriving regularly and a prompt setup, no timeout warning is expected at the start.

    So the first check at which the last valid command that the firmware has processed is at least 1000 ms old calls eStop(). The command's age at the release is therefore 1000 ms or more. eStop() sends the release to both motors over I2C, and the motor driver's library gives the firmware no confirmation that a write succeeded. A slow read() in a control step can also delay a write() that the check before it allowed, past the deadline. loop() runs its parts one after the other, and each part has to return before the next one runs. A part that blocks, for example a log message that waits for the USB connection or a slow I2C read, delays the next check. After the release, the wheels coast until friction stops them. So three moments follow each other: the commands stop, the firmware releases the motors, and the wheels come to rest.

    The command timeout doesn't cover these cases yet:

    • A firmware that hangs: the firmware never reaches the next check, and the motor driver keeps its last output.
    • A restart of the firmware: no check runs while setup() waits for the robot's computer, and the motor driver keeps its last output until begin() switches the outputs off after that wait. This follows from the order in setup() and wasn't tried on the robot.
    • A slow pass of loop(): nothing bounds how late it makes the release.
    • A failed write: the motor driver's library confirms no write, so nothing tells the firmware whether the release reached the motors.
    • The Teensy's program button or an upload: the Teensy runs its bootloader, the program that loads new firmware, instead of the firmware. Nothing on the Teensy switches the motors off.

    diffbot#190 tracks these cases. It plans a hardware watchdog: a timer in the MCU that restarts the firmware when the firmware stops resetting the timer. It also plans a second check of the command's age right before the motor write, and bench measurements of the time until the motors are released and until the wheels rest.

    Timing with the MCU's clock

    The firmware measures three kinds of elapsed time for the wheels: whether 50 ms have passed since the last control step, whether 1 s has passed since the last wheel command, and how much time has passed since the encoders' last reading. It takes all three from the MCU's own counters. millis() counts the milliseconds since the MCU started, for the control step and the command's age, and also for the IMU's samples and the debug output. micros() counts microseconds, for the encoders' speed. A correction of the Raspberry Pi's clock doesn't change these counters.

    The time stamps

    Each part keeps the millis() readings that it needs:

    • CommandTimeout keeps the arrival time of the last valid wheel command, last_command_ms_, in the CommandTimeout excerpt above.
    • WheelControl keeps the time of the last control step, last_control_ms_. last_control_ms_ starts at zero, so the first control step is due 50 ms after the MCU started. The setup takes longer, so the first pass of loop() already runs a control step. Wheel commands don't move this schedule.
    • ImuPublisher keeps the time of its last sampling slot in sampled_ms_. This time moves on also when no sample is read or published.
    • BaseController keeps the time of the last debug output in the debug field of LastUpdateTime. publishDebugIfDue() compares it with now_ms and, when debugging is on, logs once 200 ms have passed, at an UPDATE_RATE_DEBUG of 5 Hz.

    The command timeout and the control step

    The loop() excerpt above reads the counter at the start of each pass, as now_ms, and wheel_control.step(now_ms) compares it with these times:

    • The command timeout: It comes first, on every pass. CommandTimeout::update() compares the age of the last wheel command with COMMAND_TIMEOUT_MS, 1000 ms.
    • The control step: It runs when at least control_period_ms_ milliseconds have passed since the last one. WHEEL_CONTROL_CONFIG in main.cpp sets the period to 1000.0 / UPDATE_RATE_CONTROL, in whole milliseconds. With UPDATE_RATE_CONTROL set to 20 (Hz), that's 50 ms. The step records its time in last_control_ms_. So the firmware runs at most 20 steps per second. Work that blocks the loop, for example a slow serial transfer, makes a step late. A late step doesn't make up for the steps that it missed.

    When the counters wrap

    millis() and micros() return 32-bit unsigned integers. After 2³² counts they return to zero: 2³² ms (4,294,967,296 ms) is about 49.7 days, and 2³² µs about 71.6 minutes. Arduino's reference pages for millis() and micros() round these to about 50 days and 70 minutes. The differences are computed with uint32_t, so now_ms - last_control_ms_ still gives the right number of milliseconds across that return to zero, as long as the two readings are less than one counter cycle apart and come from the same run of the firmware.

    That's also why only a new command ends the command timeout. Once timed out, CommandTimeout doesn't compare the times again. So an old arrival time can't look new after the counter has gone around.

    For example, a command arrives at millis() 100 and times out at 1100. Then no command arrives for about 49.7 days, for example because the hardware interface on the robot's computer was stopped, until the clock reads 100 again. That reading alone doesn't make the old command new: 100 − 100 would give an age of 0, but CommandTimeout stays timed out. A new command that arrives at that moment does start a new timeout, because the wheel commands' callback reports every arrival to CommandTimeout.

    The same subtraction is why nh.spinOnce() comes last in loop(). loop() reads now_ms at the start of the pass, and the wheel commands' callback reads millis() again when a command arrives. If the callbacks ran between reading now_ms and the step, a command could arrive later than now_ms. Then now_ms - last_command_ms_ wouldn't be negative, but almost a whole counter cycle, about 49.7 days, and the step would take the new command as too old. With nh.spinOnce() last, the next pass reads a new now_ms after the command arrived.

    Pitfalls when measuring time on a microcontroller
    • Intervals without ROS time: Don't measure intervals with ROS time. On the MCU, nh.now() returns ROS time, which rosserial synchronizes with the robot's computer. When that computer's clock is corrected, ROS time can jump. A jump backward makes a control step or the command timeout wait too long. A jump forward makes a recent command look too old. Clock corrections on the robot's computer don't change the MCU's counters.
    • Units and types: Check the unit and type of every time value. Storing 0.05 s in an integer field for whole seconds truncates it to 0, and a check against 0 passes on every pass of the loop. Keep intervals in milliseconds or microseconds.
    • The step rate: The step rate is part of the controller. The PID controller adds up the error once per step, without the time between steps. At another rate, the same gains make the wheels respond differently. Tune the gains at the rate that the firmware runs. diffbot#168 proposes a wheel PID that is independent of the loop rate.

    Ports and adapters

    WheelControl and CommandTimeout run in the unit tests on a PC because they follow a pattern from Alistair Cockburn, ports and adapters, also called hexagonal architecture. It separates the logic from the libraries and the hardware:

    • The core contains the logic to test. WheelControl and CommandTimeout are plain C++ and include no Arduino, rosserial or vendor library headers.
    • A port defines an interaction across the core's boundary: the functions, their arguments and their required behavior.
    • An adapter connects a port to a particular environment, such as ROS, Arduino, a motor driver or a test.

    There are two kinds of ports. They differ in who calls whom:

    Primary port Secondary port
    Who calls the functions an adapter the core
    Who implements the functions the core an adapter
    Other names driving, inbound driven, outbound

    The figure shows WheelControl with its ports, once on the microcontroller and once in the unit tests. Follow the arrows from the code that calls to the code that is called. On the microcontroller, RosWheelCommandSubscriber calls receiveCommand() from its callback, loop() calls step(), and BaseController and RosTimeoutLogger implement the secondary ports. The unit tests call the primary ports themselves, and FakeBaseController and FakeTimeoutLog implement the secondary ones.

    Each port consists of these functions:

    • Primary ports: receiveCommand() and step().
    • Secondary ports: Controller, the four functions setWheelTargets(), read(), write() and eStop(), and LogTimeout, a call without arguments that logs the timeout.

    Controller and LogTimeout are hard to see in the code, because no class has these names. Each is a template parameter of WheelControl, and WheelControl's class comment (lines 27–51) says what each port has to do. The compiler checks that the type used has the functions and argument types that WheelControl calls, but not that the functions behave as the port requires. I2cBus, a port of the IMU driver, is an abstract class instead.

    double motor_constant_right_inv = (gain_ + trim_) / motor_constant_;
    double motor_constant_left_inv = (gain_ - trim_) / motor_constant_;


    joint_velocity_commands_[0] = joint_velocity_commands_[0] * motor_constant_left_inv;
    joint_velocity_commands_[1] = joint_velocity_commands_[1] * motor_constant_right_inv;


    // Publish the desired (commanded) angular wheel joint velocities
    diffbot_msgs::WheelsCmdStamped wheel_cmd_msg;
    wheel_cmd_msg.header.stamp = ros::Time::now();
    for (int i = 0; i < NUM_JOINTS; ++i)
    {
        wheel_cmd_msg.wheels_cmd.angular_velocities.joint.push_back(joint_velocity_commands_[i]);
    }

    pub_wheel_cmd_velocities_.publish(wheel_cmd_msg);

      write() takes these steps:

      1. It scales each joint's command in joint_velocity_commands_ with the gain / trim model: gain_ plus trim_ for the right wheel, gain_ minus trim_ for the left wheel, each divided by motor_constant_. The three values come from base.yaml. With a gain of 1.0, a trim of 0.0 and a motor constant of 1.0, the commands pass unchanged.
      2. It stamps the message wheel_cmd_msg with ros::Time::now(), the ROS time of the robot's computer. The firmware doesn't use this stamp: it takes a command's arrival time from the MCU's clock.
      3. It appends the left and then the right wheel's command, in rad/s, and publishes the message.

      The rest of write() publishes motor values on motor_left and motor_right for another kind of motor driver node, and logs when debugging is on. The firmware doesn't subscribe to these topics.

    These parts of the DiffBotHWInterface class let Remo work with the ROS Navigation Stack. Hardware Bringup shows how to bring up the robot hardware and how the started nodes interact with each other.
