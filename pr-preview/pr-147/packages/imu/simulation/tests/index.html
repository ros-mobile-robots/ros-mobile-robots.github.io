    IMU Simulation: Tests

    In the Gazebo simulation, DiffBot and Remo have a simulated IMU. The simulated IMU publishes on the same topic and with the same message type as the IMU on the real robot. CI checks the simulated IMU with three tests in Gazebo. This page shows what the tests check, how to run the tests yourself and what a pass proves. Read the page before you change where the simulated IMU sits in a robot's URDF model or the code that makes the IMU's message. This page belongs to IMU: Simulation, which explains that message.

    Two Python files check the simulated IMU in Gazebo, test_imu.py and test_imu_reset.py, with three tests. Each test reads the topic /diffbot/imu/data_raw:

    1. The test at rest, in test_imu.py: the robot stands still.
      • A pass shows: the message has the form that its readers need. More than 90 messages arrive in 2 s of simulation time, each stamp is later than the one before, the frame is imu_link, the orientation \(\mathbf q\) is marked unavailable, the yaw rate \(\omega_z\) and the upward reading \(f_z\) are finite, the yaw rate's variance is positive, the mean of \(f_z\) lies within 0.5 m/s² of 9.81 m/s², which is gravity, and the mean of \(\omega_z\) lies within 0.05 rad/s of 0 rad/s.
      • Why: the IMU sample validator and the EKF need the message this way, and the firmware publishes it this way.
    2. The left turn, in test_imu.py: the robot turns left on the spot at 0.5 rad/s.
      • A pass shows: more than 90 messages arrive in 2 s of the turn, and the mean of their yaw rate \(\omega_z\) lies within 0.15 rad/s of the commanded 0.5 rad/s, nominally between 0.35 and 0.65 rad/s.
      • Why: the yaw rate is the one value that the EKF fuses, and its sign has to be that of the turn.
    3. The reset test, in test_imu_reset.py: the test resets the simulation after about 3 s.
      • A pass shows: after the test saved its count of samples, just before it calls the reset, at least ten samples arrive whose stamps advance: each later than 0 s, later than the one that counted before it, and below 1 s.
      • Why: the IMU sample validator and the EKF start over at a reset and need samples right away.

    What the tests don't show lists what a pass doesn't prove. A yaw rate that stays at one value fails one of the two tests of test_imu.py: about zero fails the left turn, and about the turn rate fails at rest (what a pass of the left turn shows).

    test_imu.py has two test methods. unittest runs a test class's methods in alphabetical order. So the left turn, test_imu_measures_a_positive_yaw_rate_in_a_left_turn, runs before the test at rest, test_imu_publishes_the_firmware_message_at_rest. This page explains the test at rest first, because its checks are the simpler ones.

    Before each of the two test methods, setUp() waits until the IMU publishes and the drive controller listens to commands. Waiting until the robot can drive in the reference part of this page explains these waits.

    The test at rest

    test_imu_publishes_the_firmware_message_at_rest checks that the message on /diffbot/imu/data_raw is what its readers need. The EKF runs at 50 Hz, the firmware's rate. The IMU sample validator forwards only samples with the frame imu_link, rising stamps, finite values and a positive variance. And the firmware's message has no orientation. The robot stands still during this test, because then the reading on the upward axis, \(f_z\), is known: gravity alone.

    def send_command(self, command: Twist, seconds: float) -> None:
    """Send the command for seconds of simulation time, COMMAND_RATE times per second."""
    rate = rospy.Rate(COMMAND_RATE)
    end = rospy.Time.now() + rospy.Duration(seconds)
    while rospy.Time.now() < end:
        self.command_publisher.publish(command)
        rate.sleep()

def collect_messages(self, command: Twist, seconds: float) -> List[Imu]:
    """Return the IMU's messages of the next seconds of simulation time.

    The test sends the command during that time, so the robot keeps following it.
    """
    self.messages.clear()
    self.send_command(command, seconds)
    return list(self.messages)
    • send_command() publishes a velocity command for seconds of simulation time, 20 times per second (COMMAND_RATE). One command isn't enough: the drive controller stops the robot when no command arrives for 0.5 s.
    • collect_messages() returns the IMU's messages of the next seconds. It empties the list, sends the command for that time while the subscriber fills the list, and returns a copy of the list.

    def assert_message_rate(self, messages: List[Imu]) -> None:
    """Fail unless the messages of MEASURE came at more than RATE_TOLERANCE of RATE.

    So a mean is taken only over more than that share of the messages that RATE gives in
    MEASURE, and never over one message or none.
    """
    rate = len(messages) / MEASURE
    self.assertGreater(rate, RATE_TOLERANCE * RATE,
                       '{} published at {:.1f} Hz, expected {:.0f} Hz'.format(
                           TOPIC, rate, RATE))

    rate is \(N / T\), with \(N\) messages in \(T\) = 2 s. The check is \(N / T > 0.9 \cdot 50 \text{ Hz} = 45 \text{ Hz}\). So the test needs more than 90 messages, which is at least 91. The firmware publishes at 50 Hz, and the EKF runs at that rate. Because this check comes first, a mean is never taken over one message or none.

    def test_imu_measures_a_positive_yaw_rate_in_a_left_turn(self) -> None:

    turn_left.angular.z = TURN_RATE
    self.send_command(turn_left, SPEED_UP)

    • What the robot does: turn_left is the command, a turn on the spot at TURN_RATE, 0.5 rad/s, in the command's angular.z. send_command() sends turn_left for SPEED_UP, 1 s, so that the robot reaches the turn rate. So the nominal range of the mean is 0.35 to 0.65 rad/s. The comparison runs with floating-point numbers: a mean of exactly 0.35 or 0.65 rad/s fails, because the computed difference is 0.15000000000000002. A left turn, counterclockwise seen from above, is positive about the upward z axis, as the angular velocity shows.

    What a pass of the left turn shows

    A pass shows two things: more than 90 messages arrived in the 2 s of MEASURE, and the mean of their yaw rates lies within 0.15 rad/s of 0.5 rad/s. So the test fails when the IMU's frame is upside down, which gives about −0.5 rad/s, when the yaw rate stays near 0 rad/s, and when one message or none arrives, with the rate's message instead of an error.

    A yaw rate that stays at one value fails one of the two tests of test_imu.py: about 0 rad/s fails the left turn, and about 0.5 rad/s fails the test at rest. Neither test alone shows that the yaw rate follows the robot's motion, and together they show it only at rest and in this one turn.

    The reset test

    test_imu_reset.py checks that the IMU publishes again right after a reset of the simulation. A reset sets Gazebo's clock back to zero. A plugin that doesn't notice this stays silent for as long as the simulation ran before the reset, and the EKF gets no yaw rate in that time. Publishing again after a reset explains how the robots' plugin handles a clock that went back.

    The figure shows the stamps of the IMU's samples during the test, with the robots' IMU plugin and with a plugin that keeps the time from before the reset. The figure is an idealized example: the reset comes at exactly 3 s, and the IMU publishes exactly 50 samples per second. In a run, the reset comes a little later, for example at 3.019 s. The robot stands still in this test. What changes is the simulation's clock.

    def setUp(self) -> None:
    self.stamps: List[float] = []  # s of simulation time, in the order the samples arrived
    self.sample_count_at_reset = 0
    rospy.Subscriber(TOPIC, Imu, self.note_stamp, queue_size=QUEUE_SIZE)
    rospy.wait_for_service(RESET_SERVICE, timeout=STARTUP_TIMEOUT)
    self.reset_simulation = rospy.ServiceProxy(RESET_SERVICE, Empty)

def note_stamp(self, message: Imu) -> None:
    """Note the sample's stamp."""
    self.stamps.append(message.header.stamp.to_sec())

def imu_ran_before_reset(self) -> bool:
    """Return whether the IMU's stamps have reached RUN_BEFORE_RESET."""
    return bool(self.stamps) and self.stamps[-1] >= RUN_BEFORE_RESET

    1. Run: the test waits until the latest stamp is at least RUN_BEFORE_RESET, 3 s. The test looks at the stamps every POLL_INTERVAL, 0.02 s of wall time, so the last stamp before the reset is 3 s or a little later. In the two runs of Run the tests, the last stamp was 3.000 s and 3.019 s. last_time in the plugin then holds about that time.
    2. Reset: the test notes how many samples have arrived, in sample_count_at_reset, and calls /gazebo/reset_simulation, the highlighted line. Gazebo's clock starts from zero again.
    3. Wait for fresh samples: the test waits for FRESH_SAMPLE_COUNT fresh samples, ten here. Each poll checks the count first. If the count is still too low and the wall clock has passed RECOVERY_TIMEOUT, 30 s, the wait fails.

    def fresh_stamps(self) -> List[float]:
    """Return the advancing stamps from the first RECOVERY of simulation time after the reset.

    A stamp counts when it is later than zero, later than the last stamp that counted, and
    earlier than RECOVERY. So a stamp that repeats or goes back doesn't count. A sample that
    the IMU published before the reset can still arrive after it. Its stamp is
    RUN_BEFORE_RESET or later, so it doesn't count either.
    """
    fresh_stamps: List[float] = []
    latest_fresh_stamp = 0.0
    for stamp in self.stamps[self.sample_count_at_reset:]:
        if latest_fresh_stamp < stamp < RECOVERY:
            fresh_stamps.append(stamp)
            latest_fresh_stamp = stamp
    return fresh_stamps

def imu_recovered(self) -> bool:
    """Return whether enough fresh samples have arrived."""
    return len(self.fresh_stamps()) >= FRESH_SAMPLE_COUNT

    fresh_stamps() goes through the stamps that arrived after the test noted sample_count_at_reset, in the order of their arrival. A stamp counts when it is later than 0 s, later than latest_fresh_stamp, the last stamp that counted, and below RECOVERY, 1 s. imu_recovered() is true when ten stamps count. So a pass shows this much: after the test saved the count, at least ten samples arrived whose stamps advance and lie below 1 s. Such a stamp belongs to the new simulation time, because the stamps had reached 3 s before the reset.

    • With the robots' plugin, the first sample after the reset is stamped about 0.02 s, one period after the clock went back. Ten fresh samples then take about 0.2 s of simulation time. The test doesn't require these two values: it accepts any ten advancing stamps below 1 s.
    • With a plugin that keeps the old time, the next sample comes only after the clock has passed 3 s again. Then no sample is stamped below 1 s, and the test fails.
    • Stamps that don't advance: a stamp of 0 s, a stamp that repeats the last one that counted, and a stamp that goes back don't count. So ten samples with one and the same stamp give one fresh sample at most, and the test fails. The IMU sample validator would forward one of them at most too. A sample that the IMU published before the reset and that arrives after it has a stamp of 3 s or later, so it doesn't count either.
    • Repeated stamps: a repeat adds nothing to the count. The test can still pass if ten other stamps advance and lie below 1 s.

    After the wait, the test prints one line and then checks the result.

    What the tests don't show

    Each item says what isn't tested, why not, and what a pass therefore doesn't prove.

    • That the yaw rate follows the robot's motion: the two tests of test_imu.py check the yaw rate's mean at rest and in one left turn, as what a pass of the left turn shows explains. A yaw rate that keeps one value fails one of them, but a pass doesn't show how the yaw rate follows other motions.
    • That a repeated stamp after a reset is rare: test_imu_reset.py doesn't count a repeated stamp and needs ten advancing ones. A stream with a few repeats among them still passes.
    • That the simulation can't stall while the controllers start: the stall of gazebo_plugins' original plugin depends on timing: it needs a request of the controller spawner in the global callback queue at the moment that the plugin spins, as one request, with each plugin explains. Most starts pass, with the original too, and each test node starts the simulation once. So a pass of test_imu.py doesn't show that the deadlock is gone. The counts of many starts, with the original and with the copy, are in diffbot#185. If a start did stall, setUp() would end with an error, because no odometry comes. A longer STARTUP_TIMEOUT wouldn't help, because a stopped clock doesn't start again.
    • Which way the IMU's x and y axes point: test_imu.py checks only the upward axis: the yaw rate and the reading of gravity. A rotation of the IMU about that axis changes neither. So a pass doesn't show that the imu_rpy of the robot's URDF model is right. Without the −90° of Remo's mounting, the test would still pass.

    • The size and the direction of the horizontal acceleration: no test drives the robot forward and compares the reading with the robot's acceleration. A pass says nothing about the size and the sign of \(f_x\) and \(f_y\), the message's linear_acceleration.x and linear_acceleration.y. The EKF doesn't fuse the acceleration, but the IMU sample validator still reads it: the validator drops a sample when one of its six values isn't finite, with the sample's yaw rate.     Wall time and simulation time

    The tests wait on two clocks:

    • Wall time is the computer's clock, the time that a clock on the wall shows.
    • Simulation time is Gazebo's clock. It starts at 0 s when the simulation starts and moves on by 1 ms with every simulation step. It stands still while Gazebo starts, and for good when the simulation stalls.

    Where the two differ: the two clocks don't run at the same speed. Their ratio is Gazebo's real time factor: 1 when a second of simulation takes a second of wall time, and less than 1 when the computer is too slow for that, as Gazebo's tutorial on physics parameters explains. The test world requests real time: 1000 steps of 1 ms per second. A busy computer, such as a CI runner, reaches less. So 2 s of simulation time can take 2 s of wall time, or 5 s.

    Which clock a ROS node reads: a ROS node reads the computer's clock, unless the parameter use_sim_time is set. Then rospy.Time.now(), rospy.sleep() and rospy.Rate follow Gazebo's clock, which Gazebo publishes on the topic /clock. The ROS wiki's page on the clock describes this. The simulation's launch file enables use_sim_time by default. Python's own time.monotonic() and time.sleep() always count wall time.
