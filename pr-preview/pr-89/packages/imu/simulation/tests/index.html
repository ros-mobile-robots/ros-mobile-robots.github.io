    IMU Simulation: Tests

    What CI checks on the simulated IMU, and how the tests do it. This page belongs to IMU: Simulation.

    Two test files check the simulated IMU in Gazebo, test_imu.py and test_imu_reset.py, with three tests:

    Test What it checks Why
    The test at rest, in test_imu.py The message on /diffbot/imu/data_raw while the robot stands still: its rate, its stamps, its frame, the orientation \(\mathbf q\) marked unavailable, usable values, and gravity in the upward reading \(f_z\) The EKF and the IMU sample validator need the message this way, and the firmware publishes it this way
    The left turn, in test_imu.py The yaw rate \(\omega_z\) while the robot turns left: positive, and about as large as the commanded turn rate The yaw rate is the one value that the EKF fuses
    The reset test, in test_imu_reset.py The IMU publishes again right after a reset of the simulation The IMU sample validator and the EKF start over at a reset and need samples right away

    What the tests don't show lists what a pass doesn't prove.

    def setUp(self) -> None:
    self.messages: List[Imu] = []
    rospy.Subscriber(TOPIC, Imu, self.messages.append, queue_size=QUEUE_SIZE)
    self.command_publisher = rospy.Publisher(COMMAND, Twist, queue_size=COMMAND_QUEUE_SIZE)
    rospy.wait_for_message(TOPIC, Imu, timeout=STARTUP_TIMEOUT)
    # Gazebo's IMU publishes before the controller spawner has started the drive controller:
    # wait until the controller publishes its odometry and listens to the commands
    rospy.wait_for_message(ODOMETRY, Odometry, timeout=STARTUP_TIMEOUT)
    deadline = time.monotonic() + STARTUP_TIMEOUT
    while self.command_publisher.get_num_connections() == 0:
        self.assertLess(time.monotonic(), deadline,
                        "the drive controller doesn't subscribe to " + COMMAND)
        time.sleep(POLL_INTERVAL)
    • List[Imu]: Imu is the Python class of the message type sensor_msgs/Imu, imported from sensor_msgs.msg in line 20. Each IMU message arrives as an Imu object. List[Imu] is a type hint from Python's typing module: it says that self.messages is a list of Imu messages. Python doesn't check it when the test runs. It tells readers and tools such as mypy what the list holds.
    • The subscriber: rospy.Subscriber(TOPIC, Imu, self.messages.append, queue_size=QUEUE_SIZE) subscribes to /diffbot/imu/data_raw. Its arguments are the topic, the message class, and the callback that rospy calls for each message. The callback is the list's append method, so each message is added to self.messages. rospy runs the callback in one of its background threads, so the list fills while the test method waits. The test keeps no variable for the subscriber: rospy keeps the subscription until the node shuts down.
    • The publisher: rospy.Publisher(COMMAND, Twist, queue_size=COMMAND_QUEUE_SIZE) creates a publisher for geometry_msgs/Twist velocity commands on the drive controller's topic. self.command_publisher keeps it for the test methods.
    • The first IMU message: rospy.wait_for_message() waits for this message. The message comes early, because Gazebo's IMU sensor, the plugin and the adapter publish soon after the robot is in the simulation.
    • An IMU message doesn't mean that the robot can drive: the controller spawner starts the drive controller, mobile_base_controller, later, as the launch file on Simulation Test shows. So setUp() waits for the controller's first odometry message, which shows that the controller runs.
    • A running controller can still miss the first commands: ROS connects a publisher and a subscriber only after both exist, and a message published before the connection is lost. get_num_connections() counts the subscribers connected to the test's publisher. The loop waits until the drive controller has connected, at most STARTUP_TIMEOUT, 60 s.

    The test at rest

    test_imu_publishes_the_firmware_message_at_rest checks that the message on /diffbot/imu/data_raw is what its readers need. The EKF runs at 50 Hz, the firmware's rate. The IMU sample validator forwards only samples with the frame imu_link, rising stamps, finite values and a positive variance. And the firmware's message has no orientation. The robot stands still during this test, because then the reading on the upward axis, \(f_z\), is known: gravity alone.

    def send_command(self, command: Twist, seconds: float) -> None:
    """Send the command for seconds of simulation time, COMMAND_RATE times per second."""
    rate = rospy.Rate(COMMAND_RATE)
    end = rospy.Time.now() + rospy.Duration(seconds)
    while rospy.Time.now() < end:
        self.command_publisher.publish(command)
        rate.sleep()

def collect_messages(self, command: Twist, seconds: float) -> List[Imu]:
    """Return the IMU's messages of the next seconds of simulation time.

    The test sends the command during that time, so the robot keeps following it.
    """
    self.messages.clear()
    self.send_command(command, seconds)
    return list(self.messages)
    • send_command() publishes a velocity command for seconds of simulation time, 20 times per second (COMMAND_RATE). One command isn't enough: the drive controller stops the robot when no command arrives for 0.5 s.
    • collect_messages() returns the IMU's messages of the next seconds. It empties the list, sends the command for that time while the subscriber fills the list, and returns a copy of the list.

    The left turn

    test_imu_measures_a_positive_yaw_rate_in_a_left_turn checks the yaw rate \(\omega_z\), the one value that the EKF fuses, while the robot turns. At rest, the yaw rate is 0 however the IMU is mounted. Only a turn shows that the IMU measures the turn, and with the right sign.

    def test_imu_measures_a_positive_yaw_rate_in_a_left_turn(self) -> None:
    turn_left = Twist()
    turn_left.angular.z = TURN_RATE
    self.send_command(turn_left, SPEED_UP)

    • collect_messages() keeps the robot turning for MEASURE, 2 s, and returns the IMU's messages of that time, which the test keeps in messages. Then the test stops the robot with Twist().
    • mean_yaw_rate is the average of the yaw rates, \(\bar\omega_z\). The check needs \(|\bar\omega_z - 0.5 \text{ rad/s}| \le 0.15 \text{ rad/s}\). A left turn, counterclockwise seen from above, is positive about the upward z axis, as the angular velocity shows. So the check fails when the IMU's frame is upside down, or when the IMU doesn't measure the turn.

    The reset test

    test_imu_reset.py checks that the IMU publishes again right after a reset of the simulation. A reset sets Gazebo's clock back to zero. A plugin that doesn't notice this stays silent for as long as the simulation ran before the reset, and the EKF gets no yaw rate in that time. Publishing again after a reset explains how the robots' plugin handles a clock that went back.

    The figure shows the stamps of the IMU's samples during the test, with the robots' IMU plugin and with a plugin that keeps the time from before the reset. The figure is an idealized example: the reset comes at exactly 3 s, and the IMU publishes exactly 50 samples per second. The robot stands still in this test. What changes is the simulation's clock.

    def fresh_stamps(self) -> List[float]:
    """Return the stamps from the first RECOVERY of simulation time after the reset.

    A sample that the IMU published before the reset can still arrive after it. Its stamp
    is RUN_BEFORE_RESET or later, so it doesn't count.

    A fresh sample arrived after the test called the reset, and its stamp is earlier than RECOVERY, 1 s. A plugin that keeps the old time publishes its next sample only after the clock has passed 3 s again. Then no sample is stamped earlier than 1 s, and the test fails.

    Wall time and simulation time

    The tests wait on two clocks:

    • Wall time is the computer's clock, the time that a clock on the wall shows.
    • Simulation time is Gazebo's clock. It starts at 0 when the simulation starts and moves on by 1 ms with every simulation step. It stands still while Gazebo starts, and for good when the simulation stalls.

    Where the two differ: the two clocks don't run at the same speed. Their ratio is Gazebo's real time factor: 1 when a second of simulation takes a second of wall time, and less than 1 when the computer is too slow for that, as Gazebo's tutorial on physics parameters explains. The test's world asks for real time, with 1000 steps of 1 ms per second in lines 14–16 of diffbot_empty.world. A busy computer, such as a CI runner, reaches less. So 2 s of simulation time can take 2 s of wall time, or 5 s.

    Which clock a ROS node reads: a ROS node reads the computer's clock, unless the parameter use_sim_time is set. Then rospy.Time.now(), rospy.sleep() and rospy.Rate follow Gazebo's clock, which Gazebo publishes on the topic /clock. The ROS wiki's page on the clock describes this. The simulation's launch file sets use_sim_time, in lines 14 and 30 of diffbot_view.launch. Python's own time.monotonic() and time.sleep() always count wall time.

    When a wait in wall time runs out in test_imu.py: without an IMU message or an odometry message in time, rospy.wait_for_message() raises an exception, and the test reports an error. When the drive controller doesn't connect in time, assertLess() fails, and the test reports a failure. In test_imu_reset.py, the three timeouts only limit how long a failing run takes. The reset call has no timeout of its own, so rostest's time-limit of 180 s is its only bound.

    What the tests don't show

    Each item says what isn't tested, why not, and what a pass therefore doesn't prove.

    • That the simulation can't stall while the controllers start: the stall of gazebo_plugins' original plugin depends on timing: it needs a request of the controller spawner in the global callback queue at the moment that the plugin spins, as what goes wrong with the original plugin explains. Most starts pass, with the original too, and each test node starts the simulation once. So a pass of test_imu.py doesn't show that the deadlock is gone. The counts of many starts, with the original and with the copy, are in diffbot#185. If a start did stall, setUp() would end with an error, because no odometry comes. A longer STARTUP_TIMEOUT wouldn't help, because a stopped clock doesn't start again.
    • Which way the IMU's x and y axes point: test_imu.py checks only the upward axis: the yaw rate and the reading of gravity. A rotation of the IMU about that axis changes neither. So a pass doesn't show that the imu_rpy of the robot's URDF model is right. Without the −90° of Remo's mounting, the test would still pass.
    • The forward and the sideways acceleration: no test drives the robot forward and compares the reading with the robot's acceleration. The EKF doesn't fuse the acceleration, so nothing in the simulation depends on the acceleration yet. A pass says nothing about \(f_x\) and \(f_y\), the message's linear_acceleration.x and linear_acceleration.y.
    • The real BNO055: the simulated noise is a setting, \(\sigma\) = 0.005, and the simulated IMU has no bias and no delay. So a pass says nothing about the real sensor's noise, bias and mounting. The bench checks measure those on the robot.

    • The rest of the simulation after a reset: test_imu_reset.py checks the IMU's topic after one reset, 3 s after the start. A pass doesn't show that the other publishers come back at once. Two of them don't:

      • The drive controller's odometry: the EKF's limits on the Localization page explain why, with the times of a run.

      • The joint states: joint_state_controller publishes only when the clock has passed last_publish_time_ by one publishing period. A reset sets the clock back to zero, and last_publish_time_ keeps its value from before the reset. So the controller publishes the joint states again only when the clock has reached that time again. This follows from the controller's code and isn't measured in a run.
