    IMU Simulation: Position and Axes

    Where the simulated IMU sits on each robot, and which way its axes point. This page belongs to IMU: Simulation, which shows the IMU's message.

    The figure shows Remo. DiffBot has the same three parts, with other values. Their names come from the robot's model:

    • imu_link is the IMU's frame: a point on the robot with three axes. Every value in the IMU's message is along these axes.
    • chassis_link is the frame at the center of the robot's base plate. Its x axis points forward, its y axis to the left and its z axis up, as REP 103, ROS's convention for coordinate frames, asks for a robot's body. The models declare chassis_link in their base macro.
    • imu_joint is a fixed joint that puts imu_link on chassis_link. The joint's origin says where the sensor sits and how the sensor is turned:
      • xyz is the position in m, along chassis_link's x, y and z axes.
      • rpy is the rotation in rad: roll about x, pitch about y and yaw about z.

    The EKF needs the yaw rate along the robot's axes, not along the IMU's. The EKF converts the IMU's values with this joint's transform. robot_state_publisher publishes the transform: this ROS node reads the robot's model and publishes the position of every link to tf, ROS's system for transforms between frames. In the simulation, diffbot_control.launch starts robot_state_publisher.

    The link and the joint in the model

    The robots' models are written in xacro, XML with variables and macros. The program xacro reads such a file and writes the URDF that ROS and Gazebo use.

    A macro is a piece of model with a name and with blanks. A call names the macro and fills the blanks. Where xacro finds a call, it writes the macro's content, with the blanks filled in. So one macro can put the same part on two robots, at a different place on each.

    Both robots' models declare imu_link and imu_joint in a macro named imu_sensor. The excerpts below are DiffBot's. Remo's macro in remo_description declares the same link and joint.

    The macro's first line gives the macro's name and its blanks, which xacro calls parameters. common_sensors.xacro, line 204:

    common_sensors.xacro: the macro imu_sensor and its parameters
    204
    <xacro:macro name="imu_sensor" params="parent_link sensor_prop *origin">

    The joint in the macro uses two of the parameters, in the highlighted lines. common_sensors.xacro, lines 236–240:

    The call in DiffBot's model. diffbot.urdf.xacro, lines 80–82:

    diffbot.urdf.xacro: the call of imu_sensor
    80
81
82
    <xacro:imu_sensor parent_link="chassis_link" sensor_prop="${sensor_prop}">
  <origin xyz="$(arg imu_xyz)" rpy="$(arg imu_rpy)" />
</xacro:imu_sensor>

    How xacro puts the macro and the call together:

    1. <xacro:imu_sensor …> is the call. The name after xacro: is the macro's name.
    2. parent_link="chassis_link" fills the parameter parent_link. In the macro, ${parent_link} stands for the parameter's value. So the joint's parent becomes chassis_link.
    3. sensor_prop="${sensor_prop}" fills the parameter sensor_prop with the model's sensor settings. The joint doesn't use them. The link does.
    4. *origin is a parameter of another kind. The star says that this blank doesn't take a value in quotes. It takes a whole XML element: the element that stands between the call's opening and closing tags. Here that is the <origin … /> line. The xacro documentation calls such a parameter a block parameter.
    5. <xacro:insert_block name="origin"/> marks the place in the macro where xacro puts that element.
    6. $(arg imu_xyz) and $(arg imu_rpy) are arguments of the model file. Each has a default value, and you can set another one when you run xacro. The mounting on each robot shows their values.

    The result is this joint in DiffBot's URDF. The lines are xacro's output for diffbot.urdf.xacro at the pinned commit, with the arguments' defaults. They aren't a file in a repository:

    DiffBot's URDF, expanded by xacro: imu_joint

    <joint name="imu_joint" type="fixed">
  <parent link="chassis_link"/>
  <child link="imu_link"/>
  <origin rpy="0 0 0" xyz="0 0 0.01"/>
</joint>

    So the macro says that the IMU has a link and a joint. The call says where the joint puts the link. That is why the position and the rotation stand in each robot's model file, and not in the macro. type="fixed" means that the joint can't move: imu_link keeps its place on chassis_link, as the board keeps its place on the robot.

    The mounting on each robot

    Each robot's model file sets where its call puts the IMU. Choose your robot:

    The first picture shows Remo with the lidar platform hidden. The IMU board sits on the breadboard, at the rear. The second picture shows Remo from above. The IMU's x axis points to the right, its y axis forward, and its z axis up, toward you.

    Remo's model describes the BNO055 board on the breadboard on the Raspberry Pi deck. The diffbot repository uses Remo's model at remo_description 2.5.0, the version that diffbot_dev.repos names. The call of the macro puts the IMU on chassis_link. remo.urdf.xacro, lines 211–216:

  <origin xyz="$(arg imu_xyz)" rpy="$(arg imu_rpy)" />

    imu_xyz and imu_rpy are xacro arguments, declared at the top of the file with their defaults. remo.urdf.xacro, lines 26–27:

    • Position: −4.01 cm, +2.34 cm and +1.3 cm from chassis_link. chassis_link lies 3.6 cm behind the wheel axle, as the comment in lines 71–74 of remo.urdf.xacro explains. So the chip's center lies 7.6 cm behind the wheel axle, 2.34 cm left of the robot's center line, and 8 cm above the floor. The board's header pins sit in the breadboard.
    • Rotation: \(-\pi/2\) rad, −90°, about z. The board lies flat. Its z axis points up, its y axis forward and its x axis to the robot's right. A tilt test on Remo showed these axes, as the bench checks describe. The comment above the arguments in remo.urdf.xacro says how each value was found.

    What follows for the message's values on Remo:

    • Both z axes point up. So a left turn reads as a positive yaw rate \(\omega_z\), for the IMU as for the robot.
    • Forward is imu_link's y axis. So a forward acceleration appears in linear_acceleration.y, not in linear_acceleration.x.

    In DiffBot's URDF, the joint's origin is <origin rpy="0 0 0" xyz="0 0 0.01"/>, on chassis_link, as the expanded joint above shows. To try another mounting, override the arguments when you expand the model, for example xacro diffbot.urdf.xacro imu_xyz:='0 0 0.02'.

    What follows for the message's values in DiffBot's model:

    • imu_link lies straight above chassis_link, with the same directions. Seen from above, the two frames lie on top of each other, so this page has no figure of them.
    • Both z axes point up. So a left turn reads as a positive yaw rate \(\omega_z\).
    • Forward is imu_link's x axis. So a forward acceleration appears in linear_acceleration.x.
