    IMU Simulation: The Robots' Own Plugin

    In Gazebo, DiffBot and Remo load their own IMU plugin, not the plugin that comes with ROS. This page explains why, and what the robots' plugin does differently. The page belongs to IMU: Simulation. The page is background for the interested reader: you don't need the page to use the simulated IMU.

    Why the robots have their own plugin

    In Gazebo, a plugin turns the IMU sensor's values into ROS messages. ROS comes with one, libgazebo_ros_imu_sensor.so from the package gazebo_plugins. The robots load libdiffbot_gazebo_ros_imu_sensor.so instead. This library is the diffbot repository's copy of that plugin, taken from gazebo_plugins 2.9.3, the version that the dev container installs. The package diffbot_gazebo_plugins builds the copy from gazebo_ros_imu_sensor.cpp.

    The copy takes the same parameters, computes the same values and publishes the same message as the original. Two differences matter while the simulation runs:

    1. The copy doesn't call ros::spinOnce(): with the original, this call can stop the simulation's clock for good while the controllers start. Why the plugin doesn't spin explains how.
    2. The copy publishes again right after a reset of the simulation: the original stays silent for as long as the simulation ran before the reset. Publishing again after a reset explains why.

    The copy's other changes don't change what the plugin publishes.

    Why the plugin doesn't spin

    The short answer

    In Gazebo, one thread moves the simulation's clock forward: the physics thread. With gazebo_plugins' original IMU plugin, this thread can end up waiting for something that only it can do. Then nothing moves the clock anymore.

    The original plugin calls ros::spinOnce() right after it publishes a message. This call makes the physics thread run the service requests that wait in the node's global callback queue at that moment. The controller spawner's requests wait there. Such a request then waits for the controller manager's next update, and only the physics thread runs that update. So the physics thread waits for itself, and the simulation's clock stops for good. The robots' copy leaves the call out, because a plugin that only publishes has nothing to spin for.

    diffbot#185 has the diagnosis, with the backtraces of the stalled simulations.

    One request, with each plugin

    The two drawings follow the same request of the controller spawner, once with each plugin. Switch between the two tabs to compare them: what both runs share stays in place. The blue path is the request, and the box named update() at the bottom of the left lane is the update that the request waits for. The numbered steps below each drawing explain its numbers. The terms in the drawings explains threads, callbacks and the callback queue in more detail.

    1. The request arrives: the controller spawner calls the controller manager's service switch_controller. The spawner is a separate ROS node, which starts the robot's controllers. ROS doesn't run a service's function, its callback, at the moment the request arrives. The request waits in the Gazebo server's global callback queue, a waiting list, until a thread takes the request out and runs the callback.
    2. The physics thread publishes and spins: before a ROS spinner thread takes the request, the physics thread starts a simulation step and calls the plugin's UpdateChild(). The plugin publishes its message and calls ros::spinOnce().
    3. The callback runs in the physics thread: ros::spinOnce() runs the callbacks that wait in the global queue at that moment, in the thread that calls it. So ros::spinOnce() finds the request and runs the service's callback, in the physics thread.
    4. The callback waits: the callback notes which controllers to start, and waits until the controller manager's update() has taken the change.
    5. Nothing can end the wait: update() runs only in the physics thread. But the physics thread is still inside UpdateChild(), waiting in the callback. The physics thread waits for itself. This is a deadlock: update() never runs, the callback never returns, and the simulation step never ends. The simulation's clock stops for good, and the spawner never gets its answer.
    1. The request arrives: the request waits in the global callback queue, as with the original plugin.
    2. The physics thread publishes and returns: the physics thread calls UpdateChild(). The copy publishes its message and returns, as the header and publishing shows. So the physics thread never runs a callback.
    3. The callback runs in a spinner thread: a ROS spinner thread takes the request and runs the callback. The callback notes the change and waits, in the spinner thread.
    4. The physics thread goes on: it calls update(), in this step or the next, and update() takes the change. The clock runs on.
    5. The wait ends: the callback returns, and the spawner gets its answer. The controllers run.

    Timing: the stall depends on timing. The stall needs a request of the spawner in the queue at the moment that the original plugin spins, before a spinner thread has taken the request. So the stall hits only some starts of the simulation. diffbot#185 counts how many starts stalled with the original and with the copy.

    No spinning in the copy: the copy needs no spinning of its own, because it only publishes and has no callbacks. The spinner threads run the calls that wait in the global queue, the controller manager's among them.

    The terms in the drawings

    This section explains three terms, each with an example from the simulation, and one fact about the controller manager.

    Threads: a program can do several things at the same time, each in a thread. A thread runs one function after the other. While a thread is inside a function that waits, it can't do anything else. The threads of one program share the program's data.

    Example: the Gazebo server, gzserver, has a physics thread, which computes the simulation step by step. Each step moves the simulation's clock forward by 1 ms, the max_step_size in line 15 of the test's world file. At the start of every step, the physics thread calls the update functions of the plugins, one after the other. Two of them matter here:

    • UpdateChild() of the IMU plugin, which publishes the IMU message.
    • update() of the controller manager, which runs the controllers, such as the drive controller. The plugin gazebo_ros_control calls update(), in line 251 of its source. What runs in the simulation on Simulation Test shows how these parts work together.

    Only the physics thread calls these two functions. And the simulation's clock moves on only when the physics thread finishes a step.

    Callbacks: a callback is a function that a program gives to ROS, for ROS to run when something arrives: a message on a topic, or a request to a service.

    Example: the controller manager offers the service switch_controller, which starts and stops controllers. The service's callback is the function that does this work. When another node calls the service, the callback runs, and the caller gets its answer when the callback returns.

    The callback queue: ROS doesn't run a callback at the moment its request arrives. ROS puts the call into a callback queue, a waiting list. The queue itself runs nothing, and it isn't a thread. A thread has to take each call out of the queue and run it. ROS calls this spinning. The thread that spins is the thread that runs the callback.

    Example: the Gazebo server is one ROS node, /gazebo. A node has a global callback queue. A service's calls wait there, unless the service was given a queue of its own. The controller manager's services use the global queue. The gazebo_ros_control plugin passes its ordinary node handle to the controller manager. A node handle is how a ROS program offers topics and services. The controller manager registers its services through that handle.

    Two things can run the calls that wait in the global queue:

    • The ROS spinner threads do nothing else. Each takes a waiting call out of the global queue and runs it. Gazebo's ROS interface, the plugin gazebo_ros_api_plugin, starts one such thread per CPU core with a ros::AsyncSpinner, in line 148 of its source. The gzserver script of gazebo_ros loads this plugin into the server.
    • ros::spinOnce() spins the global queue once, in the thread that calls it. It runs the callbacks that wait in the global queue at that moment, and returns when they have returned. The ROS wiki describes single-threaded spinning. In roscpp, spinOnce() calls callAvailable() on the global queue.

    Not every service of the Gazebo server uses the global queue. Gazebo's ROS interface registers its own services, such as /gazebo/reset_simulation, on a separate queue. Its gazeboQueueThread() processes that queue. Neither the spinner threads nor ros::spinOnce() run it, and the rest of this explanation doesn't need it.

    The fact about the controller manager: its services wait for update(). The controller spawner is a separate ROS node, which diffbot_control.launch starts. The spawner loads and starts the controllers with two of the controller manager's services, load_controller and switch_controller. Their callbacks don't change the running controllers themselves, because update() may be using the controllers at that moment. The callbacks note the change and wait until update() has taken it, as the two collapsed boxes of step 4 show. switch_controller can give up after a time limit. The spawner asks for none: it passes 0 as the last argument, in line 212 of its source.

    Why not just wait?

    The deadlock comes from the physics thread running a callback that waits for the physics thread. The first three ideas below wait differently and don't remove that dependency. The fourth removes it in another place:

    • A delay, or starting Gazebo paused: a delay at the start might change which thread takes the spawner's request, but the unsafe path stays. Starting Gazebo paused doesn't help either. The controllers start only when update() takes the change, and the physics thread calls update() only while the simulation runs. So the request waits for the simulation to run, and then the same path is open. Later requests to the controller manager can take this path too.
    • A condition variable lets a thread sleep until another thread signals it. The callback already waits. Waiting on a condition variable instead of polling would still block the physics thread, which is the only thread that can run update().
    • A timeout: with a positive timeout, switch_controller can return a failure about one second after the timeout expires. The wait in step 4 shows the check and the return. The spawner passes 0, which turns the timeout off. load_controller has no timeout at all. And a failed switch wouldn't start the controllers anyway.
    • A separate queue for the controller manager, served by a thread of its own, would also keep the callbacks out of the physics thread. That would require changing the ordinary node handle that gazebo_ros_control gives the controller manager.

    The IMU plugin only publishes, so it has no callbacks of its own to run. Leaving out ros::spinOnce() is the smallest change that keeps the physics thread out of the queue. The packaged plugin has no option to turn off this call. The robots load their own library, so the fix doesn't require replacing gazebo_plugins' installed library.

    Publishing again after a reset

    A reset of the simulation sets Gazebo's clock back to zero. /gazebo/reset_simulation is the ROS service for a reset, one of Gazebo's simulation control services. For example: rosservice call /gazebo/reset_simulation.

    Both plugins limit their rate. They compare the IMU sensor's update time, current_time in the code, with last_time, the time of their last update:

    • The original has only this rate limit. After a reset, current_time starts from zero again, and last_time still holds a time from before the reset. The difference of the two is negative, so the rate limit stops every call until the clock has passed its value from before the reset. The longer the simulation ran before the reset, the longer the IMU stays silent.
    • The copy sets last_time to current_time when current_time is the earlier one. The rate limit then counts from the new time, and the plugin can publish again one period, 20 ms, later. The checks before a call publishes shows these lines.

    The copy's other changes

    The change notice at the top of the file lists every change. Besides the two differences above, the copy has these changes, which don't change what the plugin publishes:

    • The destructor uses the plugin's node handle only when Load() has created it. Load() returns before that when the sensor isn't an IMU sensor, when frameName is missing or when ROS isn't initialized. The original then calls the node handle's shutdown() through a pointer that was never set.
    • The class is in the namespace diffbot_gazebo_plugins. So a Gazebo process that loads both libraries can't mix up this class with gazebo_plugins' class of the same name, as the header's notice says.
    • The optional profiler calls are left out. This package doesn't enable them.
    • The lines are at most 99 characters long, and the file includes the header of every name it uses.

    The source is under the Apache License 2.0, as the original is. The copy keeps the original's notices, and the package installs the license's text, as its package.xml and CMakeLists.txt show. Gazebo looks for the library's file name on GAZEBO_PLUGIN_PATH and then on LD_LIBRARY_PATH. The workspace's setup.bash puts the workspace's library folder on LD_LIBRARY_PATH, as the comment in CMakeLists.txt says.
