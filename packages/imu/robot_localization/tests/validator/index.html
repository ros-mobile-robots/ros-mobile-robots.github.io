    Tests: The IMU Sample Validator

    test_imu_validator.py tests the IMU sample validator one decision at a time. Its 30 unit tests call the validator's Python class and functions directly, without a ROS master, a node or a topic. They check which samples the validator accepts, the reason for each sample that it rejects, the silence and the level that its diagnostics report, and the counts of a report. The stepped-clock test runs the node together with the EKF. This page belongs to the tests of the Localization.

    One sample through the validator

    Two examples show the validator's decision before the code. Each example gives one sample to a new validator, one that has seen no sample yet, at the ROS time \(t\) = 100 s. This is the ROS time of most tests, their constant NOW. Both samples are in the frame imu_link, with finite values and positive variances, as the firmware sends them. They differ only in their stamp \(t_s\):

    • Sample B, stamped \(t_s\) = 99.900000 s: its age \(t - t_s\) is 0.100000 s, exactly max_age. The validator accepts B, and the node forwards the sample.
    • Sample A, stamped \(t_s\) = 99.899999 s: its age \(t - t_s\) is 0.100001 s, 1 µs more than max_age. The validator rejects A as TOO_OLD, and the node drops the sample.

    The figure shows the decision's steps in the order of its arrows. A sample that meets a step's condition goes on to the next step. A sample that doesn't takes the arrow "no" to its drop reason, in a dashed red box. The numbers 1 to 5 are those of the five checks on the Localization page.

    Why B passes and A fails, how to read the figure, and the two ends of the decision

    Check 4 lets a sample through that is at most max_age, 0.1 s, old: \(t - t_s \le \texttt{max\_age}\). B is exactly that old and passes. Check 5 has no stamp of an earlier valid sample to compare B's stamp with, so B passes check 5 too, and the validator accepts B. A is 1 µs older than B and fails check 4. The same two samples appear in the test of Check 4: the two time limits, which gives both to one validator.

    The figure shows every step of the decision, in the order of its arrows. On a wide screen, the steps run from left to right in two rows. On a narrow screen, they run from top to bottom. Each step is a box with a condition. A sample that meets the condition follows the arrow to the next step. A sample that doesn't meet the condition takes the arrow "no" to the reason for which the validator rejects the sample, in a dashed red box. The second step drops no sample: after the ROS time went back, the validator sets its attributes last_valid_stamp and last_valid_arrival_time to None. These two attributes hold the stamp and the arrival time of the last valid sample. Then the decision goes on, as a clock that goes back explains. The numbers 1 to 5 are those of the five checks on the Localization page.

    The decision has two ends:

    • Accepted: drop_reason_or_record() stores the sample's stamp \(t_s\) in the validator's attribute last_valid_stamp and its arrival time \(t\) in last_valid_arrival_time, and returns None. The node counts the sample as forwarded and publishes the sample for the EKF. The tests check this end with assert_accepted().
    • Rejected: drop_reason_or_record() returns the reason. The validator stores neither the sample's stamp nor its arrival time in last_valid_stamp and last_valid_arrival_time. At a ROS time other than 0, the clock check has already stored the call's ROS time in last_checked_ros_time. The node counts the sample under this reason, which the diagnostics report, and passes a warning to rospy.logwarn_throttle() with the period WARNING_PERIOD, 5 s. The tests check this end with assert_rejected().

    What a pass proves and what a failure means

    A pass means that, for the tests' samples and times, the validator decides as the five checks describe, and that its diagnostics report the expected silence, level and counts.

    A failure names the test and the assertion, with the value that came back. The test's name says which decision went wrong, and its section below shows the test. For example, test_validator_accepts_a_sample_max_age_old_and_rejects_an_older_one expects that the validator accepts a sample exactly 0.1 s old and rejects one 1 µs older as TOO_OLD. Its failure shows which of the two decisions differed and the value that came back. The tests give the validator their own limits, so a changed launch parameter max_age doesn't make them fail.

    What the tests don't show

    • The node: no test creates an ImuValidatorNode, with its topics, parameters and lock.
    • The real clock and the real IMU: whether max_age and max_future fit the robot's USB link is a measurement on the robot.
    • Values that the validator doesn't check: a finite but implausible value passes by design.
    The details
    • The node: the class ImuValidatorNode reads the parameters, subscribes to the topic imu/data_raw, publishes on the topic imu/data_validated and on the topic /diagnostics, and reads the ROS time in a lock around each sample. The unit tests don't create an ImuValidatorNode: they call the methods of ImuValidator directly. The stepped-clock test runs the node with the EKF and checks its counts on the topic /diagnostics.
    • The real clock and the real IMU: every time in these tests is a number that the test chose. Whether max_age and max_future fit the delays of the robot's USB link is a measurement on the robot, as Limits says. The issue IMU validator: measure the samples' age on the robot, then set max_age and max_future (diffbot#219) measures it.
    • The fields that the validator doesn't check: the overview lists them. No test sends a sample with an implausible but finite value, because the validator accepts such a sample by design. The EKF doesn't drop such a value either. The first measurement initializes the filter. For each later measurement, robot_localization's EKF computes the difference between the measurement and the filter's prediction and corrects the estimate with this difference, unless a rejection threshold finds the difference too large (ekf.cpp, lines 164–189), as the same section of the overview explains. The IMU's threshold for the angular velocity, imu0_twist_rejection_threshold, defaults to the largest double (ros_filter.cpp, line 1418), and ekf.yaml sets none. So a large but finite yaw rate in a valid sample moves the estimate.

    Where the ROS time comes from

    ImuValidator never reads the ROS clock. Its methods get the ROS time \(t\) as their argument now: from the node on the robot and in the simulation, and in the tests a time that the test chooses, most often NOW, 100 s.

    The node's callback, and what the ROS clock returns

    ImuValidator never reads the ROS clock itself. Its methods drop_reason_or_record() and seconds_since_last_valid_sample() get the ROS time \(t\) as their argument now. The caller decides which time that is:

    • On the robot and in the simulation: the node's class ImuValidatorNode calls the two methods. For each sample, rospy calls the node's callback on_sample(), which reads the ROS time with rospy.Time.now() and passes it to drop_reason_or_record() as now. For each diagnostics report, the node's method take_snapshot() reads the ROS time in the same way and passes it to seconds_since_last_valid_sample().
    • In the tests: each test passes a ROS time that it chooses, most often NOW, 100 s. So a test can put any ROS time next to any stamp \(t_s\), and needs no clock and no waiting.

    def on_sample(self, message: Imu) -> None:
    """Forward message if it is valid, else drop it, count it by its reason and warn."""
    with self.lock:
        now = rospy.Time.now()
        drop_reason = self.validator.drop_reason_or_record(message, now)
        if drop_reason is None:
            self.counts.count_forwarded()
            # The publisher has a queue (queue_size), so this call doesn't wait for the
            # subscribers
            self.publisher.publish(message)
        else:
            self.counts.count_dropped(drop_reason)
    if drop_reason is not None:
        warning = 'IMU sample dropped: {} (stamp {:.3f} s, ROS time {:.3f} s)'.format(
            drop_reason.value, message.header.stamp.to_sec(), now.to_sec())
        rospy.logwarn_throttle(WARNING_PERIOD, warning)

    on_sample() stores the method's result in the variable drop_reason. The result is either None or a reason to drop the sample:

    • None: Python's value for "nothing", here "no reason to drop the sample". The node counts the sample as forwarded and publishes the sample on the topic imu/data_validated.
    • A reason: a member of DropReason. The node counts the sample by this reason with count_dropped(). After the lock, the callback passes a warning with the reason's text to rospy.logwarn_throttle() with the period WARNING_PERIOD, 5 s, which leaves out repeated warnings within that period.

    The lock self.lock around both calls keeps the diagnostics timer, which runs in another thread, from reading the validator in the middle of a sample.

    What rospy.Time.now() returns depends on the ROS parameter /use_sim_time, as the ROS wiki's page Clock explains:

    • On the robot: none of the launch files that start the robot sets /use_sim_time. Which launch file starts what on the Localization page shows these files. Without the parameter, rospy.Time.now() returns the system clock of the robot's single-board computer (SBC), in seconds since 1 January 1970. This clock doesn't read 0.
    • In the simulation: gazebo_ros's empty_world.launch, which diffbot_view.launch includes, sets /use_sim_time to true. Gazebo publishes the simulation's time on the topic /clock, and rospy.Time.now() returns the time of the last message there. Until the node has received the first message on /clock, rospy.Time.now() returns 0. Before the checks: no clock shows what the validator does then.

    The stepped-clock test sets /use_sim_time too, and publishes the messages on /clock itself.

    drop_reason_or_record(): the decision about a sample

    drop_reason_or_record(message, now) decides about one sample, stamped \(t_s\), that arrives at the ROS time \(t\), now. The method returns the first reason to drop the sample, or records the sample's stamp and arrival time and returns None.

    The two arguments, and what the name says

    drop_reason_or_record(message, now) decides about one sample. The node calls the method once for each sample, and the tests call the method through two assertions. Its two arguments are:

    • message: the sample, a sensor_msgs/Imu message. The sample carries its own time, the stamp \(t_s\) in header.stamp, which the sender writes into the message. On the robot, the Teensy's firmware stamps each sample with rosserial's ROS time when it starts to read the BNO055. That time estimates when the BNO055 measured, because the sensor doesn't report that time, as the firmware's IMU publisher explains. In the simulation, Gazebo's IMU plugin stamps each sample with the simulation time of the measurement. The header also carries the frame of the values, header.frame_id. The messages and their fields on the Localization page lists the sample's fields.
    • now: the ROS time \(t\) at which the sample arrives at the validator, a rospy.Time. The sample's way from the sender to the node takes time, so \(t\) is usually a little later than \(t_s\). On the robot, rosserial synchronizes the Teensy's clock only approximately with the SBC's clock. The remaining offset can put \(t_s\) a little after \(t\). Check 4 allows a stamp up to max_future, 0.02 s, ahead.

    The validator checks both the frame and the stamp: check 1 the frame, check 4 the stamp \(t_s\) against the ROS time \(t\), and check 5 the stamp \(t_s\) against the stamp of the last valid sample.

    The name lists the method's two outcomes in their order: the caller gets the drop reason, the first reason to drop the sample, or, when the sample has no drop reason, the method records the sample's two times and returns None. To record means here that the validator stores the sample's stamp in its attribute last_valid_stamp and the ROS time of the sample's arrival in last_valid_arrival_time, for its next decisions. The validator doesn't keep the message or write it to a file. The return type in the method's first line, Optional[DropReason], says the same: the result is a member of DropReason or None. So None means "no reason to drop": the sample is valid, and the node forwards the sample.

    def drop_reason_or_record(self, message: Imu, now: rospy.Time) -> Optional[DropReason]:
    """Return the first reason to drop message, or None for a valid sample.

    now is the ROS time at which message arrives. None means that the sample is valid. Only
    then, the method stores the sample's stamp in last_valid_stamp and now, the ROS time of
    its arrival, in last_valid_arrival_time (record_valid_sample_times()): the next sample's
    stamp has to be later, and seconds_since_last_valid_sample() counts from now. A sample
    with the same stamp is then invalid, until the clock goes back and the clock check clears
    last_valid_stamp and last_valid_arrival_time. An invalid sample leaves the two attributes
    as they are, unless the sample arrives after the clock went back. The clock check runs
    for every sample at a nonzero ROS time, valid or not: the check stores now in
    last_checked_ros_time, and clears last_valid_stamp and last_valid_arrival_time if the
    clock went back.
    """
    reason = self.drop_reason(message, now)
    if reason is None:
        self.record_valid_sample_times(message, now)
    return reason

    At the ROS time zero, the method returns NO_CLOCK and checks nothing else. At any other

    """
    # Treat zero as unavailable ROS time for samples. Return before the clock check to keep
    # last_checked_ros_time, last_valid_stamp and last_valid_arrival_time as they are
    if now.is_zero():
        return DropReason.NO_CLOCK
    self.clear_last_valid_sample_times_if_clock_went_back(now)
    for sample_check in self.sample_checks:
        reason = sample_check(message, now)
        if reason is not None:
            return reason
    return None

    drop_reason() works in three steps:

    1. No clock: if a sample arrives at the ROS time 0 s, drop_reason() returns DropReason.NO_CLOCK at once. The validator reads 0 s as "no clock yet", as the comment above this return says, so the method skips step 2, the clock check. The clock check compares the current ROS time with last_checked_ros_time, the ROS time of the last clock check. At startup, before the first message on /clock, a new validator has no earlier check. Now suppose that the validator last checked the clock at 100 s and a clock publisher sends 0 s. A sample that arrives at 0 s leaves the validator's attributes as they are: 100 s in last_checked_ros_time, and the last valid sample's stamp and arrival time in last_valid_stamp and last_valid_arrival_time. If the next check reads 0.02 s, the check sets last_valid_stamp and last_valid_arrival_time to None, because 0.02 s is earlier than 100 s. That next check can come from a sample or from a diagnostics report. A test in Before the checks: no clock and two tests of the silence check that a sample at 0 s changes none of the three attributes.
    2. A clock that went back: clear_last_valid_sample_times_if_clock_went_back(now) clears last_valid_stamp and last_valid_arrival_time if now is earlier than last_checked_ros_time. The method then stores now in last_checked_ros_time for the next clock check.
    3. The checks: the loop calls the checks in the tuple sample_checks, one after the other. The first check that returns a reason ends the loop, and the method returns that reason. The later checks don't run. When every check has returned None, the method returns None.

    Why one method runs both steps

    The node and the tests both call drop_reason_or_record(). So neither can record the times of a dropped sample or forget those of a valid one.

    What each of the two mistakes would do

    Two places in the code call drop_reason_or_record(): the node's callback on_sample(), once for each sample that arrives, and the tests, through assert_accepted() and assert_rejected(). Neither calls drop_reason() and record_valid_sample_times() itself. So neither can get the two steps wrong in one of two ways:

    • Recording a dropped sample's times: check 5 would compare later stamps with the stamp of a sample that the checks dropped. If a caller recorded the times of a sample from the future, otherwise valid samples with stamps no later than that stored stamp would be dropped as NOT_NEWER.
    • Not recording a valid sample's times: check 5 would still let the same stamp through, and the silence would keep counting from the arrival time that was recorded last. If no arrival time had been recorded, the silence would stay None. Such omissions could make the diagnostics report an error while valid samples arrive.

    The tests therefore run the same two steps as the node.

    def health(seconds_since_last_valid_sample: Optional[float], new_drop_count: int) -> Health:
    """Return the diagnostics level and message for the validator's state.

    seconds_since_last_valid_sample is what ImuValidator.seconds_since_last_valid_sample()
    returns, None without a valid sample. new_drop_count is the number of samples dropped since
    the report before. Silence is an error and comes before the warning about new drops.
    """
    if seconds_since_last_valid_sample is None:
        return Health(DiagnosticStatus.ERROR,
                      'no IMU sample forwarded yet, or since the clock went back')
    if seconds_since_last_valid_sample > SILENCE_LIMIT:
        return Health(DiagnosticStatus.ERROR,
                      'no IMU sample forwarded for {:.1f} s'.format(
                          seconds_since_last_valid_sample))
    if new_drop_count > 0:
        return Health(DiagnosticStatus.WARN,
                      'dropped {} samples since the last report'.format(new_drop_count))
    return Health(DiagnosticStatus.OK, 'forwarding samples')

    The function looks at three conditions in their order and returns at the first one that holds:

    1. No valid sample: the silence is None, before the first valid sample or since the clock went back. The function returns ERROR.
    2. A silence that is too long: the silence is longer than SILENCE_LIMIT, 1 s. The function returns ERROR, with the silence in the message.
    3. New drops: new_drop_count is more than 0. The function returns WARN, with the number in the message.

    When none of the three holds, the function returns OK. The function reads no clock and keeps no state, so each call is independent of the others.

    class SampleCounts:
    """The numbers of forwarded and dropped samples, without ROS communication."""

    def __init__(self) -> None:
        self.forwarded_count = 0
        self.drops_by_reason: Counter[DropReason] = collections.Counter()
        # The number of dropped samples that the last snapshot counted
        self.drop_count_at_last_snapshot = 0

    def count_forwarded(self) -> None:
        """Count one forwarded sample."""
        self.forwarded_count += 1

    def count_dropped(self, reason: DropReason) -> None:
        """Count one sample dropped for reason."""
        self.drops_by_reason[reason] += 1

    def take_snapshot(self,
                      seconds_since_last_valid_sample: Optional[float]) -> DiagnosticSnapshot:
        """Return the numbers for one report and start counting new drops for the next one.

        A dropped sample is new in exactly one snapshot, whatever that report's level is.
        """
        drop_count = sum(self.drops_by_reason.values())
        new_drop_count = drop_count - self.drop_count_at_last_snapshot
        self.drop_count_at_last_snapshot = drop_count
        return DiagnosticSnapshot(self.forwarded_count, dict(self.drops_by_reason),
                                  new_drop_count, seconds_since_last_valid_sample)

    take_snapshot() counts the new drops: the method adds up all dropped samples, subtracts drop_count_at_last_snapshot, the number that the snapshot before counted, and stores the new total for the next snapshot. The method copies drops_by_reason into a new dictionary, so a snapshot keeps its numbers when more samples arrive.
